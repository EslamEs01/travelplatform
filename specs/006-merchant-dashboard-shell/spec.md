## Overview

This feature opens the **merchant (travel-agency) surface** of the Travel SaaS Platform — the first dashboard experience for the travel agencies, tourism companies, and travel startups that will use the platform as a SaaS product. Until now the platform has built only the **public visitor → member** layer: the foundation and styleguide (Spec 001), the homepage (Spec 002), the discovery/monetization pages (Spec 003), the SEO/content pages (Spec 004), and the member auth/saved/alerts/profile pages (Spec 005). The constitution (Principle VIII) commits the product to a permanent multi-tenant SaaS direction with three surfaces — public website, **merchant dashboard**, and SaaS-owner admin — and this spec delivers the **foundation and overview page of the merchant dashboard surface**.

It creates a new `travel-saas-frontend/dashboard/` area and a single, fully-implemented page, `dashboard/index.html` (`data-page="merchant-dashboard"`), that is **both** a complete, client-presentable merchant overview **and** the reusable layout foundation (shell, sidebar, topbar, mobile drawer, breadcrumb, page header, footer, empty/loading patterns) that every future merchant page (deals, coupons, bookings, customers, analytics, integrations, settings) will be composed from. The page is **not** wrapped in the public website's marketing header/footer; instead it introduces an **app-like dashboard shell** — a fixed RTL sidebar of merchant modules, a working topbar (mobile menu, breadcrumb/current area, company switcher placeholder, global search, notifications dropdown, quick-add dropdown, user menu), and a mobile drawer with overlay/scrim — adapted from the **existing design language** (tokens, cards, badges, buttons, forms, modals, drawers, toasts, empty/skeleton states) and the existing `window.TUI` utilities (`toast`, `modal`, `drawer`, `validateForm`, `copyToClipboard`, `prefersReducedMotion`) and `main.js` `data-*` behaviors (`data-coming-soon`, `data-modal-open/close`, `data-drawer-open/close`, `data-copy`, `data-toast`, `data-validate`, `data-frontend-form`). No new visual identity is introduced and no existing public/member page or foundation artifact is rebuilt, removed, or downgraded.

The overview presents a believable, **clearly-mock**, frontend-only snapshot of a travel agency's operation: a welcome/agency summary (company name, current plan badge, subscription-status mock, pending-tasks note, primary CTAs), at least **8 KPI cards** (new booking requests, active deals, active coupons, customers, deal clicks, coupon copies, estimated conversions, deals nearing expiry — each with icon, label, value, trend indicator, helper text), a **recent booking requests** section (a responsive table/card hybrid of at least **8** rows with reference, customer, phone, request title, destination, amount, status, payment status, created date, assigned user, and a row action menu) backed by **status-change** and **add-note** custom modals, a **top performing deals** section (≥5), a **quick actions** panel, an **integration readiness** card (≥11 integrations with honest statuses), an **analytics preview** built from pure CSS/HTML bars and sparkline-like visuals (no external chart library), **operational alerts** (≥6), an **onboarding checklist** with a live progress indicator, a small **activity feed**, reusable **empty/loading (skeleton)** patterns, and a dashboard footer. One **new additive** JavaScript module, `src/js/dashboard.js` (dispatched by `<html data-page>`, loaded with `defer`), adds only the merchant-specific behaviors (sidebar/drawer toggle, topbar dropdowns, row action menus, status/note/assign modals, checklist toggling + progress, search mock state, and the coming-soon wiring for unbuilt modules); `src/js/main.js` and `src/js/ui.js` stay unchanged.

Critically, every surface is **explicit and honest** that this is a frontend-only prototype: the merchant is not really logged in, the data is not live, no booking is real, no analytics are real, no integration is connected, no payment is processed, no subscription is real, no notification is sent, and no scraping queue is active. All such surfaces are framed with the approved safe wording (بيانات تجريبية / مثال توضيحي / واجهة أمامية فقط / قابل للربط لاحقًا / لا توجد بيانات مباشرة في هذه النسخة / تكامل جاهز للإعداد لاحقًا / حالة تجريبية / لا يتم تنفيذ إجراءات حقيقية الآن) while making clear each surface is **integration-ready** for a future real backend, and the markup stays semantic and backend-ready for later Django templating.

## Scope

**In scope**:

- **One new, fully-implemented merchant page**, polished, production-grade, accessible, app-like, and honest:
  - `travel-saas-frontend/dashboard/index.html` — merchant overview (`data-page="merchant-dashboard"`): the dashboard **shell** (desktop sidebar, topbar, mobile drawer + scrim, main content area, breadcrumb, page header, dashboard footer) plus the complete **overview content** (welcome/agency summary, ≥8 KPI cards, recent booking requests table/card hybrid with row actions, status-change modal, add-note modal, top performing deals, quick actions, integration readiness card, analytics preview, operational alerts, onboarding checklist, activity feed, and reusable empty/loading patterns).
- **The new `dashboard/` directory** as the canonical merchant-surface location (per the constitution's file structure), with correct relative paths to the shared assets (`../assets/css/tailwind.css`, `../assets/icons/`, `../assets/images/`, `../assets/fonts/`), shared scripts (`../src/js/ui.js`, `../src/js/main.js`, `../src/js/dashboard.js`), and the public site (`../pages/index.html`, `../pages/deals.html`, `../pages/deal-details.html?id=`, etc.).
- **One new additive JavaScript module**, `travel-saas-frontend/src/js/dashboard.js`, scoped to the dashboard surface only and dispatched by `<html data-page="merchant-dashboard">`, following the precedent set by Spec 003's `discovery.js`, Spec 004's `content.js`, and Spec 005's `member.js`. It composes with `window.TUI` and the existing `main.js` `data-*` delegation and adds only merchant-specific behaviors: mobile sidebar/drawer open-close (incl. overlay/scrim), topbar dropdowns (notifications, quick-add, user menu), table row action menus, status-change modal, add-note modal, contact-customer and assign-user feedback, quick-action and integration-action toasts, onboarding-checklist toggling with progress update, and the global-search mock state. `src/js/main.js` and `src/js/ui.js` stay **unchanged** (and `discovery.js`, `content.js`, `member.js` stay unchanged).
- **Realistic, consistent mock content** as backend-ready reference data: new additive `assets/data/merchant-dashboard.json` (company, plan, subscription-status mock, KPIs, analytics-preview values, operational alerts, onboarding tasks, activity feed, notifications), `assets/data/merchant-bookings-preview.json` (≥8 booking requests with the full schema), `assets/data/merchant-deals-preview.json` (≥5 top-performing deals with merchant metrics), and `assets/data/merchant-integrations-preview.json` (≥11 integrations with status + description), plus **reuse** of existing `deals.json`, `coupons.json`, and `compare-offers.json` ids/links where a deal/coupon/route is referenced so identity stays consistent across the platform.
- **Navigation preparation for the future merchant modules**: the sidebar and every in-page entry point reference the planned future pages (`dashboard/deals.html`, `create-deal.html`, `edit-deal.html`, `coupons.html`, `create-coupon.html`, `bookings.html`, `booking-details.html`, `customers.html`, `customer-details.html`, `analytics.html`, `integrations.html`, `settings.html`) using **coming-soon** behavior (visible toast, no navigation to a non-existent file), so no control is dead and no link 404s. The single live merchant link is `الرئيسية → index.html`; the single live public link is `العودة للموقع → ../pages/index.html` (plus any public deal/compare CTAs that resolve to already-built public pages).

**Out of scope** (explicitly):

- **The future merchant pages themselves** — the full deals-management page, create/edit-deal pages, coupons-management and create-coupon pages, bookings-management and booking-details pages, customers and customer-details pages, the full analytics page, the full integrations page, and the settings page. These are **not built** in this spec; their sidebar/in-page links use coming-soon behavior only. The HTML files for them are **not created**.
- **The SaaS-owner admin surface** (companies, plans, subscriptions, platform analytics, content management, integration monitoring) — entirely out of scope and not referenced as a built page.
- Rebuilding or modifying the Spec 001 foundation (design system, shell, components, JS utilities, styleguide, components showcase) beyond additive mock-data, the additive `dashboard.js` module, additive imagery placeholders, and the new icons (if any) needed by dashboard navigation; rewriting or restructuring the Spec 002 homepage, the Spec 003 discovery pages, the Spec 004 content pages, or the Spec 005 member pages; **no existing public/member section is removed or redesigned**. `src/js/main.js`, `src/js/ui.js`, `src/js/discovery.js`, `src/js/content.js`, and `src/js/member.js` stay unchanged.
- Modifying the constitution, or introducing any new/second visual identity, color system, typography, or component style.
- **Any backend, database, real authentication, real merchant account, real merchant session, real subscription or billing, real API calls or API sync, real analytics or tracking, real booking management or persistence, real customer records, real notifications (email/WhatsApp/push), real payments, real charts from an external service, real Travelpayouts/Booking/Expedia/Skyscanner/Amadeus/Duffel/coupon-API integration, or a real scraping/review queue.** Every KPI, booking, deal metric, customer, integration status, analytics value, alert, checklist state, activity item, and notification is realistic **mock/demo** state that MUST NOT imply a real account, session, subscription, data feed, integration, notification, or payment.

## Clarifications

### Session 2026-06-02

- Q: Where does the merchant dashboard live, and how are asset/script/page paths resolved? → A: **A new `travel-saas-frontend/dashboard/` directory** (the constitution's canonical merchant location), a sibling of `pages/`. `dashboard/index.html` therefore references shared assets and scripts with a `../` prefix exactly like the public pages do from `pages/`: CSS `../assets/css/tailwind.css`; icons `../assets/icons/sprite.svg`; images `../assets/images/…`; fonts `../assets/fonts/…`; scripts `../src/js/ui.js`, `../src/js/main.js`, `../src/js/dashboard.js`; public site `../pages/index.html` (and `../pages/deals.html`, `../pages/deal-details.html?id=`, `../pages/compare.html`, etc.). Future merchant pages resolve **within** `dashboard/` (e.g., `deals.html`) but are coming-soon for now.
- Q: Is there a real merchant auth gate or login? → A: **No real auth gate.** `dashboard/index.html` is a directly-reachable standalone page that renders immediately and displays a **mock merchant identity** (e.g., company "شركة رحلات الشرق", a mock dashboard user) drawn from `merchant-dashboard.json` / inline static content. There is no real session, no redirect-if-not-authenticated behavior, and no claim that a merchant is really "logged in". The user-menu "logout" is a frontend-only toast that MAY navigate to the public site, never claiming a real session was ended.
- Q: Must the dashboard's core content render without JavaScript / without a backend? → A: **Static-HTML-first.** The page ships its baseline content (shell + welcome summary + KPI cards + booking-requests table + top deals + integrations + analytics-preview bars + alerts + onboarding checklist + activity feed + footer) as static HTML that renders and is readable with no backend and with JavaScript unavailable. JavaScript only **enhances** (sidebar/drawer toggle, topbar dropdowns, row action menus, modals, toasts, checklist toggling + progress, search mock state, coming-soon wiring). The local JSON catalogs exist as backend-ready reference/mock data; the page does **not** depend on client-side fetch to display its main content.
- Q: Where does the page logic live — extend an existing JS module or add a new file? → A: **A new additive `src/js/dashboard.js`**, scoped to the dashboard surface and dispatched by `<html data-page="merchant-dashboard">`, following the precedent that Spec 003 introduced `discovery.js`, Spec 004 introduced `content.js`, and Spec 005 introduced `member.js`. It is loaded with `defer`, reuses `window.TUI` and `main.js`'s existing global `data-*` delegation (coming-soon, modal, drawer, copy, toast, validate, frontend-form), and changes nothing in `main.js`, `ui.js`, `discovery.js`, `content.js`, or `member.js`.
- Q: How are the analytics preview "charts" built without an external chart library? → A: **Pure CSS/HTML** static visuals only — bar groups, sparkline-like rows, stacked/segmented bars, and proportion bars sized from realistic mock numbers. No `<canvas>`-based or CDN charting library, no external chart service. Each chart is labeled mock and is readable as static markup.
- Q: Does the dashboard use the public website's marketing header/footer? → A: **No.** The dashboard uses its own app shell — a merchant **sidebar** + **topbar** + **mobile drawer** + a small **dashboard footer** — and MUST NOT include the public header/drawer/marketing footer. The shell is structured to be backend-ready for later Django templates (predictable, server-renderable regions).
- Q: Is any dashboard state persisted across reloads? → A: **Frontend/session-only.** Dropdown open/close, drawer open/close, checklist toggles + progress, a mock status change on a booking row, search state, and any added note are **visual, in-memory** changes for the current view; reloading restores the mock defaults. `localStorage` MAY be used only as an optional frontend convenience, but **no copy may claim permanent or server-side storage**.
- Q: How are confirmations and secondary flows handled with no browser dialogs? → A: **Custom modals/toasts only.** The status-change modal, add-note modal, and any assign-user/confirm flow use the existing `window.TUI.modal` and toast patterns; browser `alert()`, `confirm()`, and `prompt()` are forbidden everywhere on the dashboard.
- Q: How do links to the not-yet-built merchant modules behave? → A: **Coming-soon behavior** — every sidebar item and in-page CTA targeting an unbuilt merchant page (deals, create-deal, edit-deal, coupons, create-coupon, bookings, booking-details, customers, customer-details, analytics, integrations, settings) shows a visible "coming soon" toast and does **not** navigate to a non-existent file. There are no dead controls and no 404s. The unbuilt page files are not created in this spec.

## User Scenarios & Testing *(mandatory)*

The beneficiary is a **travel-agency merchant user** (an agency owner, manager, or agent — Arabic-first, mobile-capable) who signs in (conceptually) to manage their travel business on the platform: publish and watch deals, run coupons, triage incoming booking requests, follow customers, read performance analytics, and connect data sources/integrations. This spec gives that user the **first** dashboard: an app-like home base where they can orient themselves, see the health of their business at a glance, act on the newest booking requests, judge which deals are performing, understand what integrations are ready to configure, see what needs attention, and finish onboarding — all as a believable, clearly-mock, frontend-only prototype that is backend-ready. The feature also serves the **business** by making the platform's SaaS/merchant promise concrete and client-presentable, demonstrating the full direction without faking any real account, data, integration, notification, or payment.

A travel-agency user opens `dashboard/index.html` and immediately gets a professional, app-like, Arabic-RTL dashboard. ### User Story 3 - Triage recent booking requests with row actions & modals (Priority: P2)

The merchant user opens the **recent booking requests** section to act on incoming demand. A responsive table/card hybrid lists at least **8** requests, each showing a booking reference, customer name, phone (`dir="ltr"`), the deal/request title, destination, amount, a **status** badge (New / Contacted / Pending Payment / Confirmed / Cancelled / Completed), a **payment-status** badge (Unpaid / Deposit / Paid / Refunded mock), the created date, the assigned user, and a **row action menu**. From a row's actions the user can **view details** (navigate to the future `booking-details.html` via coming-soon), **change status** (open a frontend-only status-change modal: reference, new status, note, notify-customer toggle placeholder; on save → toast and optional in-place status update, with no claim a real notification was sent), **add note** (open an internal-note modal: reference, required note textarea, note type, optional follow-up date; on valid submit → toast + inline success, not persisted), **contact customer** (toast), and **assign user** (mock modal or toast). On mobile the table becomes a stacked card layout that stays usable with no horizontal overflow. No action is dead and no browser dialog is used.

**Why this priority**: Booking requests are the **operational core** of a travel-agency dashboard — the thing a merchant most needs to act on daily — and this story proves the table/card-hybrid, row-action-menu, and status/note custom-modal patterns that future merchant pages (full bookings, customers) will reuse. It is co-important with the analytics/performance read (US4) and independently testable against the mock booking data. It exercises the no-browser-dialog rule heavily.

**Independent Test**: Open `dashboard/index.html` at 360px and desktop. Confirm the recent-booking-requests section renders at least **8** rows with reference, customer, phone (`dir="ltr"`), request title, destination, amount, a status badge from the six allowed statuses, a payment-status badge from the four allowed values, created date, assigned user, and a working row action menu; confirm the menu's actions open the status-change modal (validated, with a notify-customer toggle placeholder), open the add-note modal (required note), and show toasts for contact/assign and coming-soon for view-details — with the table collapsing to usable stacked cards on mobile, no horizontal scrolling, no dead actions, and no `alert()`/`confirm()`/`prompt()`.

**Acceptance Scenarios**:

1. **Given** the booking-requests section, **When** it loads, **Then** at least 8 rows render statically (without JavaScript), each with booking reference, customer name, phone (`dir="ltr"`), request title, destination, amount, a status badge (one of New/Contacted/Pending Payment/Confirmed/Cancelled/Completed), a payment-status badge (one of Unpaid/Deposit/Paid/Refunded mock), created date, and assigned user.
2. **Given** a row's action menu, **When** opened, **Then** it offers view-details, change-status, add-note, contact-customer, and assign-user — each is operable and none is dead; **When** view-details is activated, **Then** a coming-soon toast appears (the booking-details page is unbuilt) and no 404 occurs.

### Edge Cases

- **Very small / very large screens**: The dashboard holds from ~320px to wide desktop with no horizontal scrolling and no broken composition; the sidebar collapses to a drawer on mobile, the topbar stays usable, the KPI grid and card sections reflow to a single column, the booking-requests table becomes a stacked labeled-card layout, and the analytics-preview bars reflow without clipping.
- **Mixed-direction content in RTL**: Phone numbers, amounts/prices, dates, coupon codes, booking references, route names (e.g., Cairo → Dubai), plan names (Growth Plan), and integration brand names (Travelpayouts, Amadeus) display correctly within Arabic RTL (using `dir="ltr"` where appropriate) without misalignment.
- **Long Arabic strings**: Company name, welcome text, KPI labels/helper text, request titles, alert messages, integration descriptions, activity text, and onboarding descriptions wrap gracefully without overflowing cards, the table, the sidebar, or the grid.
- **Empty / no-data state**: The recent-booking-requests section and the operational-alerts section (and future merchant lists) handle having no data with a branded **empty state** (message + CTA), and reusable **skeleton/loading** patterns exist for dashboard cards and table rows — hidden by default but present as reusable patterns — never a blank or broken section.
- **Invalid / missing mock state**: A top deal, booking request, or activity item referencing an unknown deal/coupon/route id, or missing an optional field, MUST NOT break the page — it renders with safe fallbacks or is gracefully skipped, and its CTA still resolves to a valid page (or a coming-soon toast) rather than a dead link or a 404.
- **JavaScript unavailable**: Core dashboard content (shell, sidebar nav, welcome summary, KPI cards, booking-requests table, top deals, integrations, analytics-preview bars, alerts, onboarding checklist with default states, activity feed, footer) still renders and is readable; enhanced interactions (drawer toggle, dropdowns, row action menus, modals, toasts, checklist toggling + progress, search mock) degrade gracefully rather than leaving dead controls; native form `required` provides a validation baseline in the modals.
- **Coming-soon integrity**: Every control targeting an unbuilt merchant page (deals, create-deal, edit-deal, coupons, create-coupon, bookings, booking-details, customers, customer-details, analytics, integrations, settings) shows a visible coming-soon action and never navigates to a non-existent file; built links (`الرئيسية`, `العودة للموقع`, public deal/compare CTAs) navigate correctly.
- **Keyboard-only & assistive use**: All interactive elements (sidebar links, mobile menu button, topbar dropdowns + their items, global search, breadcrumb, KPI links, table row action menus, status/note/assign modal triggers and fields, contact/assign actions, quick-action buttons, integration actions, alert actions, onboarding checkboxes + CTAs, logout) are reachable and operable by keyboard with visible focus; dropdowns and modals manage focus and close on Escape via the existing `window.TUI`; status/progress changes are announced via `aria-live`; icon-only controls have accessible labels; the active sidebar item exposes `aria-current`.
- **Reduced-motion preference**: Drawer/dropdown/modal open-close, checklist progress transitions, skeleton shimmer, and any reveal/bar-grow animation respect the user's reduced-motion setting.
- **Duplicate / rapid actions**: Repeatedly opening/closing a dropdown or the drawer, re-toggling an onboarding item or a booking status, re-submitting a modal, or rapidly activating coming-soon links produces consistent, non-duplicated feedback (no stacked broken states).
- **Honesty consistency**: No control or copy implies a real merchant account/session, live data, a real booking, real analytics, a connected integration, a sent notification, an active API sync, an active scraping queue, a real subscription/plan billing, or a processed payment — every such surface is framed as بيانات تجريبية / مثال توضيحي / واجهة أمامية فقط / قابل للربط لاحقًا / لا توجد بيانات مباشرة في هذه النسخة / تكامل جاهز للإعداد لاحقًا / حالة تجريبية / لا يتم تنفيذ إجراءات حقيقية الآن.
