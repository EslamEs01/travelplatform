# Implementation Plan: Merchant Analytics + Integrations + Settings (Travel SaaS Platform)

**Branch**: `009-merchant-analytics-integrations-settings` | **Date**: 2026-06-04 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `specs/009-merchant-analytics-integrations-settings/spec.md`

## Summary

Complete the **merchant dashboard surface** by building its final three modules — **Analytics**, **Integrations**, and **Settings** — as **three new pages inside the existing `travel-saas-frontend/dashboard/` directory**: `analytics.html` (`merchant-analytics`), `integrations.html` (`merchant-integrations`), and `settings.html` (`merchant-settings`). Spec 006 opened this surface with `dashboard/index.html` (overview + reusable app shell) and Spec 007 built the deals/coupons modules; Spec 009 turns the last three coming-soon links into real screens. **Analytics** is a read-heavy performance workspace: page header (date-range selector + compare toggle + export-report mock + safe note), ≥10 KPI cards, CSS/static chart-like visuals (inquiries/clicks/coupon-copies/conversion over time — **no chart library**), traffic-source (≥8) + device breakdowns, a top-performing-deals table (≥8 rows), a top-destinations section (≥7), a coupon-performance table (≥8 rows, code `dir="ltr"`), customer/booking insight cards (≥6), prioritized recommendation cards (≥6), an export/report mock, empty + skeleton states, and a FAQ (≥5). **Integrations** is a configuration workspace: page header (3 CTAs + no-external-connection note), overview stats (6), category tabs/filters (7), integration cards across Affiliate / Travel APIs / Coupons / Scraping Review / Notifications / Manual (each: icon, status badge, enable/disable toggle, last-sync mock, configure + test buttons), ≥10 configure modals (Travelpayouts/Booking/Expedia/Skyscanner/Amadeus/Duffel/Coupon API/Scraping Review Queue/Email/WhatsApp), an activity log (≥8), a health panel, and a FAQ (≥6) — with prominent scraping/review honesty copy. **Settings** is a tabbed account workspace (7 sections): company profile, branding (color/slug live preview + mock upload), booking preferences, notification preferences (≥9 toggles × 3 channels), team members (≥6 with invite/change-role/disable/remove modals), security placeholders (change-password validation + 2FA placeholder + API-access placeholder + mock sessions/login-history), plan usage (≥7 bars + current plan + upgrade→coming-soon), a public-page preview, a danger zone (deactivate/reset/delete via custom confirmation modals), and a FAQ (≥6). Everything is a **frontend-only** prototype that is **explicit and honest**: nothing is really tracked, connected, validated, synced, scraped, sent, saved, invited, password-changed, 2FA-enabled, upgraded, billed, or exported — every surface uses the approved safe wording (بيانات تجريبية / واجهة أمامية فقط / مثال توضيحي / لا يتم الاتصال بأي API الآن / لا يتم حفظ الإعدادات على خادم الآن / قابل للربط لاحقًا / اختبار اتصال تجريبي / لا يتم إرسال إشعارات حقيقية / لا يتم تشغيل scraping فعليًا / كل المصادر تحتاج مراجعة قبل النشر) while staying backend-ready.

**Technical approach**: Static composition + mock content + progressive enhancement, **reusing the Spec 006–007 dashboard shell verbatim** (the same sidebar/topbar/mobile-drawer+scrim/breadcrumb/page-header/footer markup; only the active sidebar item, breadcrumb, and page header vary per page; the public marketing header/footer is never used). Each page authors its own `<head>` from the `partials/head.html` conventions (`../assets/css/tailwind.css`, Cairo font preload, favicon, theme-color, `robots noindex`) exactly like `dashboard/index.html` and the Spec 007 pages. All **core content is static HTML** so every page renders without JavaScript (Constitution III): the KPI cards, chart-like visuals, all tables, every integration card, all seven settings sections, the team table, and the usage bars ship statically; JavaScript only **enhances**. The **existing `src/js/dashboard.js` is extended additively** with three new per-page controllers dispatched by `<html data-page>` (`merchant-analytics`, `merchant-integrations`, `merchant-settings`) — adding the three pages to the module's `_DASH_PAGES` guard list and three `if (_currentPage === …)` dispatch lines — reusing the module's existing reusable primitives (`DropdownController`, the row-action-menu controller, the frontend-only form-submit wrapper, the shared confirm-modal helper, and `window.TUI.modal`/`toast`/`validateForm`/`copyToClipboard`, plus `main.js`'s `data-*` delegation incl. `data-coming-soon`/`data-copy`/`data-modal-open|close`/`data-toast`) — **without changing any Spec 006 or Spec 007 controller**. Analytics enhances with date-range active-state + custom-range apply toast (validating from≤to), a compare-period visual toggle, an export mock (toasts or a small modal), copy-code on the coupon table, and insight/recommendation action toasts/links — the displayed metrics are **static** (date-range changes the active chip + shows a toast; it does not fake a live re-query). Integrations enhances with a category filter (show/hide static cards by `data-category` + active tab `aria-selected` + `aria-live` count), pre-authored static `.modal` configure dialogs opened via `data-modal-open`/`TUI.modal` (Save/Test = mock toasts, no network), enable/disable + auto-import + manual-review toggles (visual state), and a "test all" mock toast. Settings enhances with tab/anchor section navigation (all sections present in the DOM — no-JS shows them stacked; JS shows one panel at a time and honors a `#section` deep link), `TUI.validateForm` on the company / booking / change-password / invite forms (incl. a new-password match rule), branding color + slug **live preview**, mock upload toasts (optional local object-URL preview), notification toggles, invite/change-role modals (validate → toast; role MAY update the visible cell), disable/remove + danger-zone **custom confirmation modals** (reusing the shared confirm helper / `TUI.modal`), a 2FA placeholder toggle, and an upgrade-plan **coming-soon** toast. **No browser dialogs anywhere.** Layout primitives the design system lacks (KPI-card grid, the CSS bar/sparkline/progress/stacked-percentage chart visuals, the integration card grid + category chips, the settings tab layout, plan-usage bars, and the analytics tables' table→cards transform) are realised with a **small page-scoped `<style>`** built from existing tokens — the same precedent `index.html` and the Spec 007 pages use — and the responsive-table→cards pattern is the one Spec 006/007 already use; **no external chart/table library**. New believable mock content lives in five additive backend-ready catalogs — `assets/data/merchant-analytics.json`, `merchant-integrations.json`, `merchant-settings.json`, `merchant-team.json`, `merchant-usage.json` — reusing `deals.json`/`merchant-deals.json`/`merchant-coupons.json` ids where a deal/coupon/destination is referenced so identity stays consistent; the static HTML matches the catalogs (no runtime fetch for baseline — III). The shared dashboard nav is **rewired (links only)** so the now-built pages navigate for real — التحليلات → `analytics.html`, التكاملات → `integrations.html`, الإعدادات → `settings.html` — across the shell (including Spec 006 `index.html`'s sidebar + quick-add + any analytics/integration/settings overview CTAs, and the Spec 007 pages' sidebars); the **Spec 006 overview and Spec 007 pages' sections/layout/copy are not removed or redesigned**, and the still-unbuilt pages stay coming-soon: the bookings/customers pages (intended Spec 008 — files absent) and the SaaS-owner admin/billing/support surface (out of scope) keep `data-coming-soon` behaviour (no 404). The only icon touch is **additive sprite symbols** for surfaces the sprite lacks (e.g., mail/whatsapp/key/lock/credit-card/palette/link/activity/building/award/pie-chart/map-pin/shield); existing icons (bar-chart/plug/settings/bell/users/trend-up|down/filter/sliders/upload/download/refresh/wand/percent/clock/copy/eye/edit/external/globe/tag/ticket/calendar/shield-check/check-circle/close/search/chevron-down/more) are reused. **`tailwind.config.js` needs no change** — its `content` globs already include `./dashboard/**/*.html` (added in Spec 006). **No behavioral change** is made to `src/js/main.js`, `src/js/ui.js`, `src/js/discovery.js`, `src/js/content.js`, or `src/js/member.js`; no existing public/member page or Spec 006/007 section is removed; no new visual identity; no backend.

## Technical Context

**Language/Version**: HTML5, CSS3 authored via the existing Tailwind CSS v3.4 local build (PostCSS/Autoprefixer); vanilla JavaScript (ES2020, classic `defer` scripts — no bundler). Build-time runtime: Node.js ≥ 18 LTS + npm (unchanged from Spec 001–007).
**Primary Dependencies**: None added. Reuses installed `tailwindcss@^3.4`, `postcss`, `autoprefixer`, `@tailwindcss/forms`; the existing `window.TUI` namespace (`toast` / `modal.open|close` / `drawer.open|close|toggle` / `validateForm(form,{rules})` / `copyToClipboard` / `prefersReducedMotion`); `main.js`'s declarative `data-*` delegation (`data-coming-soon`, `data-modal-open|close`, `data-drawer-open|close|drawer`, `data-copy`/`data-copy-target`, `data-toast`/`data-toast-type`, `data-validate`/`data-frontend-form`/`data-success-toast`, `data-year`); and the Spec 006/007 `dashboard.js` primitives (`DropdownController`, the row-action-menu controller, the frontend-only form-submit wrapper, the shared confirm-modal helper, the sidebar/drawer + topbar-dropdown wiring). **No runtime framework, no CDN, no external chart/table library** — all chart-like visuals are pure CSS/HTML. The category filter, tab navigation, modals, toggles, and forms operate on the in-page DOM; the JSON catalogs are backend-ready reference data and the baseline content does **not** depend on `fetch` (a page MAY read an inline `<script type="application/json">` block or a `#section` hash for enhancement only).
**Storage**: N/A — no backend/database/CMS/account store. Mock content is realistic, clearly-mock **static HTML** mirroring five new local `assets/data/*.json` files (`merchant-analytics.json`, `merchant-integrations.json`, `merchant-settings.json`, `merchant-team.json`, `merchant-usage.json`; `deals.json`/`merchant-deals.json`/`merchant-coupons.json` referenced unchanged). All state (date-range/compare selection, category filter, tab selection, toggle states, typed form values, a changed team-member role, color/slug preview) is **in-memory/session-only**; reload restores mock defaults; nothing is persisted to a server. `localStorage` MAY be an optional convenience only and no copy claims permanent/server storage (لا يتم حفظ الإعدادات على خادم الآن).
**Testing**: Manual QA against the per-page "done" checklist (`quickstart.md`) + automated accessibility audit (axe-core) targeting WCAG 2.1 AA, HTML validation (`html-validate`) for all three pages, and Prettier/Stylelint. The stack-compliance grep (forbidden tech + browser dialogs + external chart/table library + external CDN) is a hard gate. No unit-test framework (consistent with Spec 001–007). A `qa-results.md` is produced after implementation.
**Target Platform**: Modern evergreen browsers — Chrome, Edge, Firefox, iOS/macOS Safari — last 2 major versions. Mobile-first (~320–360px up to desktop); the pages must feel close to a native app on mobile (the analytics tables collapse to stacked labeled cards; the KPI grid, chart visuals, integration card grid, settings tabs, and forms reflow to one column).
**Project Type**: Static frontend web application (single project). This phase builds the **analytics + integrations + settings modules** of the merchant surface: three new pages in the existing `dashboard/` directory. No backend tier.
**Performance Goals**: Each page interactive in < 2s under Lighthouse mobile "Slow 4G" (≈1.6 Mbps, 150 ms RTT) + 4× CPU throttle; minified CSS reused; lazy non-critical images; zero runtime CDN requests; **no external chart/table library** (CSS-only visuals); category filter / tab navigation / modals / toggles / forms operate on the in-page DOM (no network).
**Constraints**: Approved stack ONLY (no React/Vue/Angular/Bootstrap/jQuery/Tailwind-CDN; **no external chart/table library**; no `alert()`/`confirm()`/`prompt()`); Arabic-RTL default + English-ready; WCAG 2.1 AA; standalone backend-ready pages (render without JS, structured for later Django templating); no dead interactions (coming-soon for the still-unbuilt bookings/customers + SaaS-owner admin/billing pages — no 404s); SEO/semantics baseline (semantic HTML, single `<h1>` per page, heading hierarchy, breadcrumb, meta; `robots noindex` acceptable for these merchant surfaces); **product-honesty wording** (بيانات تجريبية / واجهة أمامية فقط / مثال توضيحي / لا يتم الاتصال بأي API الآن / لا يتم حفظ الإعدادات على خادم الآن / قابل للربط لاحقًا / اختبار اتصال تجريبي / لا يتم إرسال إشعارات حقيقية / لا يتم تشغيل scraping فعليًا / كل المصادر تحتاج مراجعة قبل النشر; never a real analytics/tracking, connection, validation, sync, scrape, send, save, invitation, password change, 2FA, upgrade, charge, or export). **Reuse the Spec 006–007 shell verbatim** and the Spec 001–007 foundation unchanged except: additive `dashboard.js` extension, five additive JSON catalogs, additive sprite icons, and **link-only** rewiring of the analytics/integrations/settings entry points in the shared shell (incl. Spec 006 `index.html` + the Spec 007 pages). Preserve the visual identity; remove no existing section; **do not use the public marketing header/footer**.
**Scale/Scope**: Three new pages in the existing `dashboard/` surface. Mock data: five new backend-ready catalogs (analytics summary + time series + traffic/device + top-deals + destinations + coupon-performance + insights/recommendations; integrations across 6 categories + activity log; company/branding/booking/notification settings; ≥6 team members; ≥7 usage rows), reusing `deals.json`/`merchant-deals.json`/`merchant-coupons.json` ids where referenced. Per-page minima — **analytics.html**: header (date-range 6 options + compare + export + safe note); ≥10 KPI cards; 4 over-time visuals; ≥8 traffic sources; 3-device breakdown; top-deals table **≥8 rows** (10 cols); ≥7 destinations; coupon table **≥8 rows** (10 cols, code `dir="ltr"`); ≥6 insight cards; ≥6 recommendation cards; export mock; empty + skeleton; FAQ (≥5). **integrations.html**: header (3 CTAs + note); 6 overview stats; 7 category tabs; integration cards across all categories (≥24 named cards); ≥10 configure modals; activity log **≥8**; health panel; FAQ (≥6). **settings.html**: header (save/reset + note); 7-section nav; company form (validated); branding (color/slug preview + mock upload); booking prefs; ≥9 notification toggles × 3 channels; team table **≥6** + invite/change-role/disable-remove modals; security (change-password + 2FA + API + sessions/login-history); plan usage **≥7** bars + plan + upgrade→coming-soon; public preview; danger zone (3 confirm modals); FAQ (≥6). Navigation: rewire 3 built links across the shell; keep bookings/customers + admin/billing coming-soon.

*No `NEEDS CLARIFICATION` items remain — the spec's Clarifications (2026-06-04) resolved the ten open questions (page location & `../` paths; Spec 006–007 shell reuse; additive `dashboard.js`; static-HTML-first; CSS-only charts; session-only state; custom modals / no dialogs; mock connect/configure/test/sync + scraping honesty; mock save/upload/invite/password/2FA/upgrade/delete; link-only rewiring + coming-soon for unbuilt pages incl. the absent Spec 008 bookings/customers).
