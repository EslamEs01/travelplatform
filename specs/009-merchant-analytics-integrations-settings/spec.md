## Overview

This feature completes the **merchant (travel-agency) dashboard surface** of the Travel SaaS Platform. Spec 006 opened that surface with the reusable app shell + overview (`dashboard/index.html`); Spec 007 built the first real management modules (`deals.html`, `create-deal.html`, `edit-deal.html`, `coupons.html`, `create-coupon.html`). This spec delivers the final three modules a travel agency needs to run its business on the platform: **Analytics** (understand performance), **Integrations** (prove the product can grow into real travel-data and monetization sources), and **Settings** (manage company profile, branding, booking preferences, notifications, team, security, and plan usage).

It creates **three new, fully-implemented pages** inside the existing `travel-saas-frontend/dashboard/` directory — `analytics.html`, `integrations.html`, and `settings.html` — each reusing the **exact merchant dashboard shell** established in Spec 006 and carried through Spec 007 (the same RTL sidebar, topbar with notifications/quick-add/user dropdowns, mobile drawer + scrim, breadcrumb, page header, and dashboard footer), composed from the Spec 001 design language (tokens, cards, badges, buttons, forms, modals, drawers, toasts, empty/skeleton states) and the existing `window.TUI` utilities (`toast`, `modal`, `drawer`, `validateForm`, `copyToClipboard`, `prefersReducedMotion`) plus the `main.js` `data-*` behaviors. No new visual identity is introduced; no Spec 001–007 artifact is rebuilt, removed, or downgraded; the public website header/footer is never used on these dashboard pages.

The **analytics** page is a read-heavy performance workspace: a page header with date-range + compare + export-report controls, ≥10 KPI cards, several **CSS/static chart-like visuals** (no external chart library) for inquiries/clicks/coupon-copies/conversion over time, traffic-source and device breakdowns, a top-performing-deals table (≥8 rows), a top-destinations section, a coupon-performance table (≥8 rows), customer/booking insight cards, prioritized recommendation cards, an export/report mock, empty/skeleton states, and a help FAQ (≥5). The **integrations** page is a configuration workspace that demonstrates how the agency could later connect travel **affiliate** tools, **travel APIs**, **coupon** sources, a **scraping review** workflow, and **notification** channels: a page header with global CTAs, overview stats, category tabs/filters, integration cards across all categories (each with status, enable/disable toggle, last-sync mock, configure + test-connection buttons), a set of ≥10 configure modals (Travelpayouts, Booking, Expedia, Skyscanner, Amadeus, Duffel, Coupon API, Scraping Review Queue, Email, WhatsApp), an activity log (≥8 events), a health panel, and a FAQ (≥6) — with prominent, honest copy that no source is connected, no data is scraped, and nothing is published automatically. The **settings** page is a tabbed account workspace covering company profile, branding (with color/slug live preview + mock upload), booking preferences, notification preferences, a team-members table (≥6) with invite/change-role/disable/remove modals, security placeholders (change-password validation, 2FA placeholder, sessions/login-history mock), plan usage bars + current plan + upgrade CTA, a public-page preview card, a danger zone (deactivate/reset/delete via custom confirmation modals), and a FAQ (≥6).

All page logic is added to the existing `src/js/dashboard.js` **additively only** (no rewrite, no behavior change to existing dashboard features), dispatched per page by `<html data-page>` (`merchant-analytics`, `merchant-integrations`, `merchant-settings`); the Spec 006 and Spec 007 controllers stay unchanged, and `src/js/main.js`, `src/js/ui.js`, `src/js/discovery.js`, `src/js/content.js`, and `src/js/member.js` stay unchanged. The sidebar/topbar/quick-add links for the now-built pages (التحليلات → `analytics.html`، التكاملات → `integrations.html`، الإعدادات → `settings.html`) are **rewired to real navigation** across the dashboard shell (including the Spec 006 `index.html` and the Spec 007 pages), with correct active-state (`aria-current`) on each new page. New backend-ready mock catalogs are added under `assets/data/`, reusing existing catalogs (`deals.json`, `merchant-deals.json`, `merchant-coupons.json`) where useful; static HTML remains the source of baseline content.

Critically, every surface is **explicit and honest** that this is a frontend-only prototype: analytics are demo numbers (not real tracking), no integration is really connected, no API key is validated, no sync/scraping is running, no coupon is imported, no email/WhatsApp is sent, no setting is saved to a database, no team invitation is sent, no password is changed, no 2FA is enabled, no subscription is upgraded, no billing is processed, and no export file is really generated. All such surfaces use the approved safe wording (بيانات تجريبية / واجهة أمامية فقط / مثال توضيحي / لا توجد بيانات مباشرة في هذه النسخة / لا يتم الاتصال بأي API الآن / لا يتم حفظ الإعدادات على خادم الآن / قابل للربط لاحقًا / إعداد تجريبي / اختبار اتصال تجريبي / لا يتم إرسال إشعارات حقيقية / لا يتم تشغيل scraping فعليًا / كل المصادر تحتاج مراجعة قبل النشر) while keeping each surface **integration-ready** for a future real backend and the markup semantic and backend-ready for later Django templating.

## Clarifications

### Session 2026-06-04

- Q: Where do the three pages live and how are paths resolved? → A: **Inside the existing `travel-saas-frontend/dashboard/` directory**, as siblings of `index.html` and the Spec 007 pages. Each page references shared assets/scripts with a `../` prefix exactly like Specs 006–007: CSS `../assets/css/tailwind.css`; icons `../assets/icons/sprite.svg`; images `../assets/images/…`; data `../assets/data/…`; scripts `../src/js/ui.js`, `../src/js/main.js`, `../src/js/dashboard.js`; public site `../pages/index.html`, `../pages/deal-details.html?id=<id>`, `../pages/destinations.html`. Inter-dashboard links resolve **within** `dashboard/` (e.g., `deals.html`, `coupons.html`, `analytics.html`, `integrations.html`, `settings.html`).
- Q: Do these pages reuse the existing shell or define a new one? → A: **They reuse the exact Spec 006–007 merchant dashboard shell** — the same sidebar (brand + nav with the correct active item per page via `aria-current`), topbar (mobile menu button, breadcrumb/current area, company switcher, global search, notifications/quick-add/user dropdowns), mobile drawer + scrim, breadcrumb, page header region, and dashboard footer — and **must not** use the public website's marketing header/footer.
- Q: Where does the page logic live? → A: **The existing `src/js/dashboard.js` is extended additively only.** New per-page controllers are dispatched by `<html data-page>` (`merchant-analytics`, `merchant-integrations`, `merchant-settings`); no existing Spec 006/007 behavior is changed; `main.js`/`ui.js`/`discovery.js`/`content.js`/`member.js` are untouched; all scripts load with `defer`; no inline page JavaScript except JSON-LD or a safe inline JSON/mock-data block.
- Q: Must the pages render without JavaScript / without a backend? → A: **Static-HTML-first.** Each page ships its baseline content as static HTML that renders and is readable with no backend and with JavaScript unavailable: KPI cards, chart-like visuals, tables, integration cards, settings sections, team table, usage bars, and FAQs all render statically. JavaScript only **enhances** (date-range/active-state, compare toggle, export mock, category filter, configure/test modals, toggles, tab navigation, form validation, color/slug preview, copy, confirmations). The pages do **not** depend on client-side fetch to display their main content; the JSON catalogs are backend-ready reference data only.
- Q: Are charts drawn with a library? → A: **No.** All chart-like visuals are pure **CSS/static HTML** (bars, sparkline-style bars, progress lines, stacked percentage bars, CSS cards). No external charting/table library and no runtime CDN is used anywhere.
- Q: Is any state persisted across reloads? → A: **Frontend/session-only.** Date-range/compare selection, category filter, toggle states, typed form values, a changed team-member role, color/slug preview, and tab selection are visual/in-memory changes for the current view; reloading restores the mock defaults. `localStorage` MAY be used only as an optional frontend convenience, but **no copy may claim permanent or server-side storage** (لا يتم حفظ الإعدادات على خادم الآن).
- Q: How are confirmations, "generate", and secondary flows handled with no browser dialogs? → A: **Custom modals/toasts only.** Configure modals, save/test feedback, team invite/change-role, disable/remove confirmations, danger-zone confirmations, and export feedback use the existing `window.TUI.modal`/toast patterns; browser `alert()`, `confirm()`, and `prompt()` are forbidden everywhere on these pages.
- Q: How are integration "connect/configure/test/sync" and notification "send" actions made honest? → A: **All are mock.** "Test connection" / "test all" / "test message" validate the on-screen form (where present) and show a clearly-labeled frontend-only toast (اختبار اتصال تجريبي — لا يتم الاتصال بأي مصدر خارجي) but never make a network call. "Save configuration" shows a mock toast and never persists or validates a credential. Statuses (Connected mock / API Ready / Needs configuration / Needs review / Coming soon / Disabled / Not connected) are demo labels. The scraping/review surfaces state plainly that no data is scraped here, sources must respect their policies, nothing is published automatically, and all imported content requires manual review before publishing.
- Q: How are settings "save", "upload", "invite", "change password", "2FA", "upgrade", and "delete" made honest? → A: **All are mock.** Save/reset show mock toasts and do not persist (لا يتم حفظ الإعدادات على خادم الآن). Logo/cover upload buttons show a mock toast (لا يتم رفع ملفات حقيقية الآن); a local object-URL preview MAY be shown for UX only. Invite/change-role validate then show a toast (no invite is sent); role change MAY update the visible row only. Change-password validates the three fields client-side then shows a mock toast (no password is changed). 2FA is a placeholder toggle (no 2FA is enabled). Sessions/login-history are mock lists. The upgrade CTA shows a **coming-soon** toast because the SaaS-owner billing surface is not built. Danger-zone actions (deactivate / reset / delete) open custom confirmation modals and, on confirm, show a frontend-only warning toast — no destructive action actually happens.
- Q: Which navigation links are rewired, and what happens to still-unbuilt pages? → A: **Only the now-built analytics/integrations/settings links are rewired to real navigation** (across the dashboard shell, including Spec 006 `index.html` and the Spec 007 pages), each with correct `aria-current` on its own page. **The bookings/customers pages (intended Spec 008) and the SaaS-owner admin/billing/support pages are not built and their files do not exist**, so every control targeting them keeps **coming-soon** behavior (visible toast, no navigation to a non-existent file). No control is dead and no link 404s. (The user-supplied rewiring list named bookings/customers; because those files are absent from the repository, this spec keeps them coming-soon per the "only rewire links to pages that now exist" rule rather than creating dead links.)

### Edge Cases

- **JavaScript disabled**: all baseline content (KPI cards, chart-like visuals, tables, integration cards, settings sections, team table, usage bars, FAQs) renders and is readable; only enhancements (filters, toggles, modals, validation, preview, copy) are unavailable.
- **Custom date range with from > to (or empty)**: the apply action validates and shows an inline/toast message instead of producing a broken range; no crash.
- **Category filter that matches nothing** (if a future category is empty): an empty/placeholder state appears rather than a blank region.
- **Configure modal opened, edited, then cancelled**: no toast claims a save; closing restores focus to the triggering control.
- **Required field left blank on company/booking/password/invite forms**: submit is blocked with inline `aria-invalid` + message; no mock toast fires until valid.
- **New-password ≠ confirm-password**: validation blocks the mock save and explains the mismatch.
- **Toggling enable/disable or 2FA rapidly**: the visual state stays consistent and announces via `aria-live`; no duplicate toasts pile up.
- **Coupon copy when clipboard is unavailable**: a graceful fallback message/toast appears; no uncaught error.
- **Deep-linking to a settings section anchor** (e.g., `settings.html#team`): the matching section is shown/scrolled to on load.
- **Very long company name / slug / team email**: layout does not overflow horizontally at 360px; text truncates or wraps.
- **Activating a still-unbuilt destination** (bookings/customers/admin/billing): a coming-soon toast appears; no navigation to a missing file.

## Assumptions

- **Spec numbering & the 008 gap**: This feature is numbered **009** at the user's explicit request even though no `specs/008-…` directory exists. The intended Spec 008 (merchant bookings + customers — `bookings.html`, `booking-details.html`, `customers.html`, `customer-details.html`) has **not** been created in this repository (no spec directory and no HTML files). This spec therefore treats bookings/customers as **still-unbuilt** and keeps their navigation **coming-soon**; it does not create or depend on them beyond referencing booking/customer data for analytics demo content.
- **Navigation rewiring resolution**: The user-supplied rewiring list named bookings/customers alongside analytics/integrations/settings, but also required "only rewire links to pages that now exist" and "keep still-unbuilt pages coming-soon." Because the bookings/customers files are absent, only analytics/integrations/settings links are rewired to real navigation; bookings/customers remain coming-soon to avoid dead links/404s (constitutional No-Dead-Interactions).
- **Shell source of truth**: The merchant dashboard shell, `window.TUI` utilities (`toast`, `modal`, `drawer`, `validateForm`, `copyToClipboard`, `prefersReducedMotion`), the `data-*` behaviors, the `data-coming-soon` toast pattern, and `src/js/dashboard.js` already exist from Specs 006–007 and are reused as-is; this spec only extends `dashboard.js` additively and rewires links.
- **Charts**: All chart-like visuals are implemented with CSS/static HTML (bars, sparkline-style bars, progress lines, stacked percentage bars, CSS cards); no charting library is added.
- **Mock data scale**: Each new catalog contains enough records to back the stated minimums (≥10 KPIs, ≥8 deal rows, ≥8 coupon rows, ≥7 destinations, ≥8 activity events, ≥6 team members, ≥7 usage bars), reusing existing `deals.json`/`merchant-deals.json`/`merchant-coupons.json` ids where referenced for identity consistency; static HTML is the source of baseline content and the JSON is backend-ready reference only.
- **Tailwind config**: The existing `./dashboard/**/*.html` content glob already covers these new pages, so `tailwind.config.js` needs no change; a small page-scoped `<style>` block MAY be used for layout specifics (KPI/chart grids, percentage bars, integration card grid, settings tabs, usage bars) consistent with the Spec 007 approach.
- **Optional persistence**: `localStorage` MAY be used only as a frontend convenience for the current session; no copy claims server-side persistence.
- **English readiness**: Pages are Arabic-first RTL with English-ready structure; a full English localization layer is out of scope for this spec (structural LTR soundness only).
- **Brand/company demo identity**: The company profile, branding, team, plan, and usage values are realistic demo content for a single example agency; no real tenant/account exists.
