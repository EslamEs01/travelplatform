## Overview

This feature builds the **public SEO and content layer** of the Travel SaaS Platform — the destination-discovery and travel-guide pages that the homepage (Spec 002) and the discovery pages (Spec 003) gesture toward but, until now, could only reach through the "coming soon" affordance. It adds four real, standalone public pages — a **destinations listing** (`destinations.html`), a **destination details** landing (`destination-details.html`), a **blog / travel-guides listing** (`blog.html`), and a **single article** page (`article.html`) — and then **rewires the homepage and shared navigation** so the destination and blog/guide links that should now resolve to these real surfaces stop showing the "coming soon" toast and instead navigate to the new pages.

Every page is composed **entirely on top of the existing foundation** — the same Arabic-first RTL shell (top bar + slide-in drawer + footer), the same design tokens, the same reusable components (buttons, cards, badges, modals, drawers, toasts, form fields, skeletons, empty states), and the same `window.TUI` interaction utilities and `data-*` behaviors used by the homepage and the discovery pages. No new visual identity is introduced; no foundation artifact or homepage section is rebuilt, removed, or downgraded. The pages reuse and extend the existing realistic mock data (deals, coupons, compare-offers, destinations) and add two new mock-content catalogs (`destinations-full.json`, `articles.json`) so that any deal, coupon, destination, or article referenced across the homepage and discovery pages stays consistent here.

This phase completes the **public visitor's content & discovery layer**: from the homepage or anywhere in the shell, a traveler can now browse the full set of destinations, open any destination to read a rich, SEO-strong landing that links it to related deals, coupons, comparison, an itinerary, and travel guides, browse the travel-guides blog, and read a full long-form Arabic article that points back into deals, coupons, comparison, and destinations — all as believable, clearly-mock, frontend-only, integration-ready experiences with zero dead interactions. The page set proves the platform has genuine **SEO depth** and is not merely a deal-listing site, while never claiming that prices, routes, coupon guarantees, visa rules, or availability are live or official.

## Scope

**In scope**:

- Four new standalone public pages, fully implemented, polished, production-grade, and SEO-rich:
  - `travel-saas-frontend/pages/destinations.html` — searchable, filterable destinations listing (region + travel-style chips) with popular routes, seasonal ideas, an SEO content block, a guides teaser, a destination-alert form, FAQ, empty state, and skeleton state.
  - `travel-saas-frontend/pages/destination-details.html` — rich single-destination landing (default: Dubai) with hero, quick-facts, related deals, related coupons, a price-trend teaser, best areas/neighborhoods, things-to-do, long-form travel-guide content, a 3-day itinerary, related articles, a destination-alert modal/form, and FAQ.
  - `travel-saas-frontend/pages/blog.html` — searchable, filterable travel-guides listing (category chips) with a featured article, an article grid, a popular-guides/sidebar block, an SEO content section, a guide-alert form, FAQ, empty state, and skeleton state.
  - `travel-saas-frontend/pages/article.html` — long-form SEO article (default: "كيف تجد أرخص عروض السفر إلى دبي؟") with article header, table of contents, substantial Arabic body, an inline related-deal card, an inline copyable coupon card, related destinations, related articles, a newsletter/price-alert form, and FAQ.
- Realistic, consistent mock content the pages need: two **new additive** catalogs — `assets/data/destinations-full.json` (≥12 destinations, rich schema) and `assets/data/articles.json` (≥12 articles) — plus reuse of the existing `deals.json`, `coupons.json`, `compare-offers.json`, and the homepage teaser `destinations.json`, and page-only imagery placeholders (local SVG).
- One **new additive** JavaScript module, `travel-saas-frontend/src/js/content.js`, scoped to these four pages only (search/filter chips, URL query state, result-count announcements, `destination-details.html?id=` and `article.html?id=` content swap, table-of-contents scroll, save/bookmark toggles, alert/newsletter form validation) — following the precedent set by Spec 003's `discovery.js`. It composes with the existing `window.TUI` utilities and `data-*` behaviors and changes no existing behavior.
- **Homepage and shared navigation rewiring**: updating the header/drawer/footer "الوجهات" (Destinations) and "المدونة" / "دليل السفر" (Blog/Guides) links, the homepage popular-destination teaser cards (→ `destination-details.html?id=`), and the homepage travel-guide teaser cards (→ `article.html?id=`), plus footer destination/blog links, so the controls that should now point to these real pages navigate to them instead of using the "coming soon" toast. Controls that target surfaces still not built (auth/login/register, saved deals, standalone price-alerts management, merchant dashboard, SaaS owner admin, and any about/contact/privacy/terms not yet built) keep the "coming soon" affordance.

**Out of scope** (explicitly):

- Rebuilding or modifying the Spec 001 foundation (design system, shell, components, JS utilities, styleguide, components showcase) beyond additive mock-content data, the additive `content.js` module, and additive imagery placeholders.
- Rewriting or restructuring the Spec 002 homepage; **no existing homepage section is removed or redesigned**. Homepage changes are limited to rewiring destination/blog links/CTAs (and minimal supporting hooks) so they reach the new pages.
- Rebuilding or modifying the Spec 003 discovery/monetization pages (`compare.html`, `deals.html`, `coupons.html`, `deal-details.html`) or their `discovery.js` behavior; this spec only **links into** them. `src/js/main.js` and `src/js/ui.js` stay unchanged.
- Modifying the constitution or introducing any new/second visual identity, color system, typography, or component style.
- Login / register / auth pages, saved-deals page, standalone price-alerts management page, member/traveler dashboard, merchant (travel agency) dashboard, and SaaS owner admin pages — all remain out of scope and keep their "coming soon" affordance.
- Any backend, database, real CMS, real APIs, real Travelpayouts/Booking/Expedia/Skyscanner/Amadeus/Duffel integration, real scraping, real payments, real authentication, real booking confirmation, real notifications, real WhatsApp/email sending, or real AI recommendations. All destinations, prices, routes, deal/coupon counts, seasonal data, charts, travel tips, visa notes, and availability are realistic editorial/mock content and MUST NOT imply live/real/official data.

## Clarifications

### Session 2026-06-01

- Q: How is a specific destination or article selected, and what happens when the parameter is missing or invalid? → A: **URL query parameter, `?id=` primary** — `destination-details.html?id=<destination-id>` and `article.html?id=<article-id>` are read client-side against the mock catalogs; a slug form (`?destination=<slug>` / `?article=<slug>`) MAY also be accepted. When the parameter is absent, unknown, or invalid, the page renders a **sensible default** (Dubai for the destination page; the default article "كيف تجد أرخص عروض السفر إلى دبي؟" for the article page) — never a broken or empty page. This mirrors Spec 003's `deal-details.html?id=` pattern.
- Q: Must the pages' core content render without JavaScript, or may it depend on client-side fetch/render? → A: **Static-HTML first** — each page ships its baseline/default content as static HTML that renders and is readable with no backend and with JavaScript unavailable. JavaScript only **enhances** (search, filter chips, URL state, content swap for `?id=`, copy, save/bookmark, TOC scroll, modals, form validation, toasts). Local JSON catalogs exist as backend-ready reference/mock data and to power the `?id=` swap, but pages do NOT depend on client-side fetch to show their main content.
- Q: Where does the new page logic live — extend `discovery.js` or add a new file? → A: **A new additive `src/js/content.js`**, scoped to the four new pages only, following the precedent that Spec 003 introduced `discovery.js` for its four pages. It reuses `window.TUI` and `data-*` patterns, is loaded with `defer`, and changes nothing in `main.js`, `ui.js`, or `discovery.js`.
- Q: How is the destinations dataset organized so the homepage teaser, discovery pages, and the new pages stay consistent? → A: **A new additive `assets/data/destinations-full.json`** (≥12 destinations, rich schema) is the catalog for the destination pages; the existing homepage teaser `destinations.json` and the discovery pages' references remain a **consistent subset** (overlapping destinations reuse the same id/name/country so nothing contradicts across pages). Articles live in a **new additive `assets/data/articles.json`** (≥12). Related deals/coupons referenced from destinations/articles reuse the existing `deals.json` / `coupons.json` ids.

## User Scenarios & Testing *(mandatory)*

The beneficiary is a **public visitor / prospective traveler** (Arabic-first, mobile-dominant) who arrives — from search engines, the homepage, or the discovery pages — wanting to explore where to travel, understand a destination in depth, read trustworthy travel guidance, and connect that content to deals, coupons, comparison, and a future booking inquiry. The feature also serves the **business** by turning the homepage's destination/guide promises into real, SEO-strong, content-rich public pages that demonstrate the platform's editorial depth and feed organic discovery — all backend-ready and never faking live data.

### User Story 1 - Browse, search & filter travel destinations (Priority: P1) 🎯 MVP

A visitor opens the **destinations listing** to discover where they could travel. They see a rich grid of believable destination cards (each with imagery, city/country, region, a short SEO description, an illustrative "starting from" price, best season, deals/coupons counts, travel-style badges, a visa/travel note, and a clear "explore destination" CTA plus a secondary deals/compare CTA), and they can **search by city or country**, **filter by region and travel style** (chips), **reset** all filters, and understand when no destination matches (a branded empty state) or while content is settling (a loading/skeleton state). The page also surfaces popular routes, seasonal travel ideas, an SEO content block on how to choose a destination, a travel-guides teaser, and a destination-alert form. Every card and control does something observable.

**Why this priority**: The destinations listing is the canonical new "listing page" and the core surface that proves the platform's SEO depth beyond deals. It is the most self-contained, independently valuable slice — a visitor can discover and shortlist destinations on its own — and it establishes the listing contract (search/filter/empty/skeleton/reset) the blog listing reuses. This is the demonstrable MVP of the content phase.

**Independent Test**: Open `destinations.html` at 360px and at desktop. Confirm it renders Arabic RTL with a single `<h1>` ("الوجهات السياحية"), a breadcrumb (الرئيسية / الوجهات), a grid of at least **12** destination cards (with imagery + meaningful alt, region, illustrative pricing using safe wording, best season, deals/coupons counts, travel-style badges, a visa/travel note, and a CTA to `destination-details.html?id=`), working search and region/style chips that narrow the visible set with a live-announced result count, a visible reset that restores the full set, a branded empty state when filters exclude everything, and a skeleton state — with no horizontal scroll and no dead controls.

**Acceptance Scenarios**:

1. **Given** a visitor on a 360px phone, **When** `destinations.html` loads, **Then** it renders Arabic RTL with one primary heading, a breadcrumb, and a grid of at least 12 believable destination cards (imagery + alt, city/country, region, short SEO description, illustrative "starting from" price using safe wording, best season, deals/coupons counts, travel-style badges, visa/travel note, primary + secondary CTA) — with no horizontal scrolling.
2. **Given** the destinations listing, **When** the visitor types in the search field and/or activates region/style chips, **Then** the visible destinations narrow to only those matching, the active chips are visibly indicated, and the result count updates and is announced via an `aria-live` region.
3. **Given** active search/filters that match nothing, **When** the result set is empty, **Then** a branded empty state appears with a clear reset-filters action and a path to deals/compare — never a blank or broken section.
4. **Given** applied search/filters, **When** the visitor activates reset, **Then** all search/filters clear and the full default destination set returns with the count restored.
5. **Given** any destination card, **When** the visitor activates its primary CTA, **Then** it navigates to that destination's details page (`destination-details.html?id=…`) — never a dead link, and never a browser dialog.
6. **Given** any destination card, **When** the visitor activates the save/favorite control, **Then** its state visibly toggles with feedback — never a dead control or browser dialog.

**Why this priority**: The destination details page completes the discovery → consideration funnel for content, satisfies the constitution's detail-page contract (main info + primary CTA + related items + FAQ) and SEO-depth principle, and is the platform's richest SEO landing surface. ### Edge Cases

- **Very small / very large screens**: All four pages hold from ~320px to wide desktop with no horizontal scrolling and no broken composition; listing grids, the destination-details rich layout, the price-trend teaser, the itinerary, the table of contents, and the article body reflow gracefully. The TOC remains usable on the smallest screens (e.g., collapses or stacks rather than crowding the body).
- **Mixed-direction content in RTL**: Latin destination/area names (Downtown Dubai, Dubai Marina), prices, dates, reading times, coupon codes (`dir="ltr"`), and any English tokens display correctly within Arabic RTL without misalignment; coupon codes remain legible and copyable.
- **Long Arabic strings**: Destination descriptions, area descriptions, article titles/excerpts, guide-content paragraphs, itinerary details, and FAQ answers wrap gracefully without overflowing cards, the grid, the TOC, or the article column.
- **No results / empty data**: The destinations listing and the blog listing handle an empty result set (from search/filtering or absent data) with a branded empty state and a clear reset/return action — never a blank screen.
- **Unknown or missing `?id=`**: `destination-details.html` with an unknown/absent/invalid id falls back to the Dubai default; `article.html` with an unknown/absent/invalid id falls back to the default article — never a broken or empty page, and the breadcrumb/heading/title reflect the resolved content.
- **JavaScript unavailable**: Core content of each page (the static default destination, the static default article, destination/article card content and links, headings, footer, FAQ via native `<details>` where used) still renders and is readable; enhanced interactions (search, filter chips, URL state, `?id=` swap, copy, save/bookmark, TOC scroll, modal, form validation, toasts) degrade gracefully rather than leaving dead controls.
- **Slow or missing images**: Image areas reserve space (no layout shift), use a placeholder/skeleton and lazy-loading where useful, and every image has meaningful alternative text.
- **Keyboard-only & assistive use**: All interactive elements (search, filter chips, reset, card CTAs, save/bookmark, copy controls, TOC links, share buttons, modal/alert triggers, form fields) are reachable and operable by keyboard with visible focus; modals/drawers manage focus via the existing `window.TUI`; result/empty-state changes are announced via `aria-live`; icon-only controls have an accessible label.
- **Reduced-motion preference**: Card hover, filtering transitions, TOC smooth-scroll, and any reveal animations respect the user's reduced-motion setting.
- **Duplicate / rapid actions**: Repeatedly copying a code, re-applying filters/search, re-toggling save, re-submitting a form, or rapidly clicking share produces consistent, non-duplicated visible feedback (no stacked broken states).

## Assumptions

- **Scope is these four public content pages plus navigation wiring**: This spec adds only `destinations.html`, `destination-details.html`, `blog.html`, and `article.html`, and rewires the homepage/shared navigation to reach them. Auth/login/register, saved deals, standalone price-alerts management, member dashboard, merchant dashboard, SaaS owner admin, and any unbuilt about/contact/privacy/terms pages remain out of scope and keep the "coming soon" affordance.
- **Foundation, homepage, and discovery pages are reused, not rebuilt**: Spec 001 (local Tailwind build, Arabic-first RTL shell, header/drawer/footer, design tokens, reusable components, `window.TUI` utilities and `data-*` behaviors), Spec 002 (the homepage and its mock-data files), and Spec 003 (the discovery pages, `discovery.js`, `deals.json`, `coupons.json`, `compare-offers.json`) are complete and consumed as-is. Additive mock-content data files, additive imagery placeholders, and one additive `content.js` module are permitted; no existing shared behavior, homepage section, or discovery page is changed or removed; `main.js` and `ui.js` are untouched.
- **New JS module mirrors the discovery.js precedent**: Page logic lives in a new additive `src/js/content.js` scoped to the four new pages, loaded with `defer`, composing with `window.TUI`; `discovery.js` is not modified (Spec 004 pages may, however, link into Spec 003 pages).
- **Static-HTML-first**: Each page's default/baseline content (destinations grid, default Dubai destination, blog grid, default article) is authored as static HTML that renders without a backend and without JavaScript; JS only enhances (search, filter, URL state, `?id=` swap, copy, save, TOC scroll, modals, validation, toasts).
