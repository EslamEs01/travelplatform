## Overview

This feature builds the **public member layer** of the Travel SaaS Platform — the account-style surfaces that the homepage (Spec 002), the discovery/monetization pages (Spec 003), and the SEO/content pages (Spec 004) gesture toward (save a deal, "تسجيل الدخول", "إنشاء حساب", create a price alert) but, until now, could only reach through the "coming soon" affordance. It adds five real, standalone public pages — a **login** page (`login.html`), a **register** page (`register.html`), a **saved items hub** (`saved-deals.html`), a **price-alerts management** page (`price-alerts.html`), and a **member profile/settings** page (`profile.html`) — and then **rewires the shared shell and homepage navigation** so the auth and member calls-to-action that should now resolve to these real surfaces stop showing the "coming soon" toast and instead navigate to the new pages.

Every page is composed **entirely on top of the existing foundation** — the same Arabic-first RTL shell (top bar + slide-in drawer + footer), the same design tokens, the same reusable components (buttons, cards, badges, modals, drawers, toasts, form fields, skeletons, empty states), and the same `window.TUI` interaction utilities (`toast`, `modal`, `drawer`, `validateForm`, `copyToClipboard`, `prefersReducedMotion`) and `data-*` behaviors used by the homepage, the discovery pages, and the content pages. No new visual identity is introduced; no foundation artifact or existing page section is rebuilt, removed, or downgraded. The pages reuse the existing realistic mock data (deals, coupons, destinations, compare-offers, articles) and add three new mock catalogs (`member-saved.json`, `price-alerts.json`, `member-profile.json`) as backend-ready reference data, so that any deal, coupon, destination, comparison, or article referenced from the member pages stays consistent with the rest of the platform.

This phase completes the **public visitor → member experience** as a believable, clearly-mock, frontend-only prototype: a visitor can open a premium **login** or **register** screen (with full client-side validation, password visibility, a forgot-password modal, social-login placeholders, and a membership-benefits panel), land on a **saved items hub** that organizes saved deals, coupons, destinations, comparisons, and articles into switchable tabs (each item removable, with branded empty states and coupon copy), **create, edit, pause/activate, and delete mock price alerts** through validated forms and custom modals, and **edit a profile** with personal details, travel preferences, notification toggles, and a security placeholder — all with visible toast/inline feedback and zero dead interactions. Critically, every page is **explicit and honest** that this is a frontend-only prototype: no real account is created, no real session exists, nothing is stored on a server, no email/WhatsApp notification is sent, and no price is really monitored — while making clear each surface is **integration-ready** for a future real accounts/notifications backend.

## Scope

**In scope**:

- Five new standalone public pages, fully implemented, polished, production-grade, accessible, and honest:
  - `travel-saas-frontend/pages/login.html` — premium split-layout member sign-in (`data-page="login"`): login form (email + password + remember-me + forgot-password), password-visibility toggle, forgot-password modal, membership-benefits panel, frontend-only honesty block, social-login placeholders, and a submit loading state.
  - `travel-saas-frontend/pages/register.html` — premium split-layout member registration (`data-page="register"`): registration form (name, email, phone, password, confirm password, preferred destination, travel interest, budget range, notification method, terms), password-rules panel, password-visibility toggles for both password fields, membership-benefits/preferences-preview panel, and a frontend-only honesty note.

  - `travel-saas-frontend/pages/price-alerts.html` — frontend-only price-alerts management (`data-page="price-alerts"`): hero, stats cards, a validated create-alert form with method-dependent fields, at least 6 existing alert cards with edit/pause-activate/delete/view-deals/compare actions, an edit-alert modal, a custom delete-confirmation modal, a "how alerts work" section, a branded empty state, and a FAQ.
  - `travel-saas-frontend/pages/profile.html` — member profile/settings (`data-page="profile"`): profile header with mock identity + quick links, an account sub-navigation, a validated personal-information form, a travel-preferences form, notification-settings toggles, a security placeholder (change-password form, 2FA placeholder, mock active-sessions list, logout), a privacy/data note, and a member-benefits card.

It composes with the existing `window.TUI` utilities and `data-*` behaviors and changes no existing behavior. `src/js/main.js`, `src/js/ui.js`, `src/js/discovery.js`, and `src/js/content.js` stay **unchanged**.
- **Shared navigation & homepage rewiring**: updating the header desktop "تسجيل الدخول" CTA and the drawer "تسجيل الدخول" / "إنشاء حساب جديد" CTAs to point to `login.html` / `register.html`; adding member entry points (account/saved/alerts/profile) into the shell where appropriate without removing any existing element; and rewiring any "create price alert" / "saved" / "account" affordances that should now resolve to `price-alerts.html` / `saved-deals.html` / `profile.html`. Controls that target surfaces still not built (merchant dashboard, SaaS owner admin, and any about/contact/privacy/terms/partners pages not yet built) keep the "coming soon" affordance.

**Out of scope** (explicitly):

Changes to those pages/partials are limited to additive member/auth navigation rewiring (and minimal supporting hooks). `main.js`, `ui.js`, `discovery.js`, and `content.js` stay unchanged.
- Modifying the constitution or introducing any new/second visual identity, color system, typography, or component style.
- Merchant (travel agency) dashboard and SaaS owner admin pages, and any unbuilt about/contact/privacy/terms/partners pages — all remain out of scope and keep their "coming soon" affordance.
- **Any real authentication, backend session, database, real user account, real password reset, real social login, real email/WhatsApp sending or notification, real price monitoring, real API calls, real Travelpayouts/Booking/Expedia/Skyscanner/Amadeus/Duffel integration, real payments, server-side saved items, server-side user profile, or server-side notifications.** All sign-in/registration, saved items, price alerts, profile data, and notification settings are realistic **mock/demo** state that MUST NOT imply a real account, real session, real storage, real monitoring, or real notification.

## Clarifications

### Session 2026-06-02

- Q: Do the member pages require a real "logged-in" gate, and where does member identity come from? → A: **No real auth gate.** All five pages are directly reachable standalone public pages and render their content immediately. `saved-deals.html` and `profile.html` display a **mock member identity** (e.g., name "زائر تجريبي" / a demo email) drawn from `member-profile.json` / inline static content; there is no real session, no redirect-if-not-authenticated behavior, and no claim that a member is "logged in" for real. Login/register "success" is a frontend-only confirmation, never a real session.
- Q: Is any state persisted across reloads (e.g., `localStorage`), or is it session-only? → A: **Frontend/session-only by default.** Saved-item removals, created/edited/deleted alerts, paused/activated alerts, toggled notification settings, and saved profile changes are **visual, in-memory** changes for the current page view; reloading restores the mock defaults. Copy MUST frame this as تجريبية. `localStorage` MAY be used purely as an optional frontend convenience, but **no copy may claim permanent or server-side storage** regardless. Core/default content always renders statically without JavaScript and without any stored state.
- Q: On a valid login/register submit, does the page navigate to `saved-deals.html` or just show inline success? → A: **Both supported, honesty-first.** On valid submit the page shows a success **toast + inline success** message (frontend-only, "لا يتم إنشاء حساب/جلسة حقيقية") whose primary CTA links to `saved-deals.html` (and a secondary path to the homepage). The page MAY navigate to `saved-deals.html` after confirming, but MUST NOT imply a real session was created. No forced silent redirect that mimics real authentication.
- Q: Must the member pages' core content render without JavaScript, or may it depend on client-side fetch/render? → A: **Static-HTML first.** Each page ships its baseline content (auth forms, member header + the initial set of saved items, the initial set of alert cards, the profile forms with mock values) as static HTML that renders and is readable with no backend and with JavaScript unavailable. JavaScript only **enhances** (validation states, password visibility, tabs, item removal + empty-state toggling, coupon copy, alert create/edit/pause/delete, toggles, modals, toasts, logout). Local JSON catalogs exist as backend-ready reference/mock data; pages do NOT depend on client-side fetch to show their main content.
- Q: Where does the new page logic live — extend `content.js`/`discovery.js` or add a new file? → A: **A new additive `src/js/member.js`**, scoped to the five member pages only, following the precedent that Spec 003 introduced `discovery.js` and Spec 004 introduced `content.js`. It reuses `window.TUI` and `data-*` patterns, is loaded with `defer`, and changes nothing in `main.js`, `ui.js`, `discovery.js`, or `content.js`. `main.js`'s existing global `data-*` delegation (coming-soon, drawer, modal, copy, toast, validate, frontend-form) is reused as-is; `member.js` adds only the new member-specific behaviors (tabs, item removal, alert CRUD, toggles, logout).
- Q: No browser dialogs — how are confirmations (e.g., delete an alert) handled? → A: **Custom modal only.** Delete confirmation, edit, and forgot-password use the existing `window.TUI.modal` pattern; browser `alert()`, `confirm()`, and `prompt()` are forbidden everywhere. All feedback uses toasts, modals, drawers, or inline messages.

## User Scenarios & Testing *(mandatory)*

The beneficiary is a **public visitor / prospective member-traveler** (Arabic-first, mobile-dominant) who, after exploring deals, coupons, comparisons, destinations, and guides, wants a personal home base: a place to "sign in" or "create an account", keep their favorite deals/coupons/destinations/comparisons together, set up alerts for prices they care about, and tune their travel preferences and notifications. The feature also serves the **business** by turning the platform's account/save/alert promises into a real, believable, client-presentable member experience that demonstrates the full SaaS direction and is backend-ready — while never faking a real account, session, notification, or stored data.

### User Story 1 - Sign in & create a member account experience (Priority: P1) 🎯 MVP

A visitor opens the **login** page to access the member experience and, if new, the **register** page to create one. On login they see a premium split layout (form panel + benefits/trust panel), enter an email and password (with a show/hide password toggle), can tick "remember me", open a **forgot-password modal**, submit with full client-side validation and a button loading state, and — on valid input — get a frontend-only success (toast + inline) that points them to the saved-items hub. Social-login buttons are clearly placeholders (disabled or "coming soon" toast), never implying real Google/Apple sign-in. On register they fill a fuller form (name, email, phone, password + confirm with visibility toggles and a password-rules panel, preferred destination, travel interest, budget range, notification method, and a required terms checkbox), and on valid input get the same honest frontend-only success. Both pages prominently explain that no real account or session is created and the experience is integration-ready.

**Why this priority**: Login and register are the **entry to the member layer** and establish its non-negotiable honesty contract (no real auth/session) and its premium first impression. They are the most self-contained, independently valuable slice — a visitor can experience the full account-creation/sign-in flow on its own — and they set the form-validation, password-visibility, and modal patterns the other member pages reuse. This is the demonstrable MVP of the member phase.

**Independent Test**: Open `login.html` and `register.html` at 360px and desktop. Confirm each renders Arabic RTL with a single `<h1>` ("تسجيل الدخول" / "إنشاء حساب"), a breadcrumb, a premium split layout that stacks cleanly on mobile, a fully client-validated form (email format, required fields, password minimum, confirm-password match, required terms on register), a working password-visibility toggle (both fields on register), a working forgot-password modal (login) that validates an email and shows toast + inline success, social-login placeholders that never imply real auth, a membership-benefits panel, an explicit frontend-only honesty block, and — on valid submit — a success toast + inline success linking to `saved-deals.html` — with no horizontal scroll, no dead controls, and no browser dialog.

**Acceptance Scenarios**:

1. **Given** a visitor on a 360px phone, **When** `login.html` loads, **Then** it renders Arabic RTL with one `<h1>` ("تسجيل الدخول"), a breadcrumb (الرئيسية / تسجيل الدخول), a split layout (form + benefits/trust panel) that stacks cleanly, an email field (`type="email"`, `dir="ltr"`), a password field with a show/hide toggle, a remember-me checkbox, a forgot-password trigger, a submit button, and a link to `register.html` — with no horizontal scrolling.
2. **Given** the login form, **When** the visitor submits with an empty/invalid email or empty password, **Then** the invalid fields show visible error states (`aria-invalid`, programmatically-linked messages) and the form does not "succeed"; **When** the visitor submits valid input, **Then** a success toast + inline success message appears (frontend-only, no real-session claim) with a primary CTA to `saved-deals.html`.
3. **Given** the password field, **When** the visitor activates the show/hide toggle, **Then** the password text visibility flips and the toggle's accessible label/state updates — never a dead control.
4. **Given** the forgot-password trigger, **When** activated, **Then** a custom modal opens with an email field and a note that no real email is sent in this static version; **When** a valid email is submitted, **Then** a toast + inline success appears and **When** invalid, the field shows an error — never a browser dialog.
5. **Given** the social-login placeholders (e.g., Google/Apple), **When** activated, **Then** they are visibly disabled or show a "coming soon" toast and never imply a real social sign-in.
6. **Given** a visitor on `register.html`, **When** they submit, **Then** all required fields validate (name, email format, non-empty phone, password minimum length, confirm-password match, required terms checkbox), both password fields have working visibility toggles, a password-rules panel is shown; on valid input a frontend-only success (toast + inline) appears with a CTA to `saved-deals.html`, and no copy claims a real account was created.

### User Story 3 - Create & manage frontend-only price alerts (Priority: P2)

The visitor opens the **price-alerts** page to set up alerts for destinations, flights, hotels, and packages — clearly understanding the alerts are frontend-only in this prototype and integration-ready for a future real monitoring/notification backend. They see a hero (with CTAs to create an alert, browse deals, and compare), stats cards (active / paused / triggered-mock alerts, destinations watched, average target budget), and a validated **create-alert form**: alert type (Flight / Hotel / Package / Destination), "from" city when Flight, a required "to"/destination, a required travel month, a required max budget, travelers count, a notification method (Email / WhatsApp placeholder / Dashboard only) with a method-dependent required email or phone field, and optional notes. On valid submit they get a toast + inline success and (where simple) a new mock alert card appended — never a claim of a real notification. Below the form, at least **6** existing alert cards show type, route/destination, target price, current sample price, a status badge (Active / Paused / Triggered mock), travel month, travelers, the notification method, a last-checked mock date, a "مثال توضيحي" source note, and actions to **edit** (modal), **pause/activate** (toggle), **delete** (custom confirmation modal), **view matching deals**, and **compare**. A "how alerts work" section, a branded empty state when all alerts are deleted, and a FAQ (≥5 honest Q&As) complete the page.

**Why this priority**: Price alerts are the second pillar of the member value proposition and the platform's clearest "we'll watch this for you (later)" promise; the page proves the full create/read/update/delete loop as a believable prototype and exercises the custom-modal-instead-of-browser-dialog rule most heavily. It is co-important with the saved hub (US2) and independently testable against mock alert data.

**Independent Test**: Open `price-alerts.html` at 360px and desktop. Confirm it renders Arabic RTL with one `<h1>` ("تنبيهات الأسعار"), a breadcrumb (الرئيسية / تنبيهات الأسعار), a hero explaining frontend-only + integration-ready with CTAs to `deals.html`/`compare.html`, stats cards, a validated create-alert form with method-dependent fields (email required when Email, phone required/placeholder when WhatsApp, "from" shown when Flight), ≥6 alert cards with the specified fields/status badges/actions and a "مثال توضيحي" note, a working edit modal (validated), a working pause/activate toggle, a custom delete-confirmation modal that removes the card and shows a toast, a branded empty state when all alerts are deleted, and a FAQ with ≥5 entries — with no horizontal scroll, no dead controls, and no browser `alert()`/`confirm()`/`prompt()`.

### User Story 4 - Manage profile, travel preferences & notification settings (Priority: P3)

### Edge Cases

- **Very small / very large screens**: All five pages hold from ~320px to wide desktop with no horizontal scrolling and no broken composition; the auth split layouts stack cleanly on mobile, the saved-hub tabs and card grids reflow, the price-alert form and cards reflow, and the profile multi-section forms remain usable and comfortably tappable (≥ ~44px targets).
- **Mixed-direction content in RTL**: Email addresses, phone numbers, coupon codes (`dir="ltr"`), prices, dates, budgets, route names (e.g., Cairo → Dubai), and any English tokens display correctly within Arabic RTL without misalignment; coupon codes remain legible and copyable.
- **Long Arabic strings**: Member name/welcome text, saved-item titles, alert routes/notes, preference labels, FAQ answers, and honesty notes wrap gracefully without overflowing cards, tabs, the forms, or the grid.
- **Empty / removed-to-zero state**: Every saved-items tab and the price-alerts list handle becoming empty (via removal/deletion or absent data) with a branded empty state — message, CTA to the relevant page, and an optional mock-restore action — never a blank or broken section.
- **Invalid / missing mock state**: A saved item or alert referencing an unknown deal/coupon/destination/article id, or missing optional fields, MUST NOT break the page — the item renders with safe fallbacks or is gracefully skipped, and its CTA still resolves to a valid page (or the listing) rather than a dead link.
- **JavaScript unavailable**: Core content of each page (auth forms, member header + initial saved items, initial alert cards, profile forms with mock values, footer, FAQ via native `<details>` where used) still renders and is readable; enhanced interactions (validation states, password visibility, tabs, removal, copy, alert CRUD, toggles, modals, toasts, logout) degrade gracefully rather than leaving dead controls. Native form `required`/`type=email` provide a baseline without JS.
- **Method-dependent form fields**: On the create-alert form, switching alert type (Flight reveals "from") and notification method (Email requires email; WhatsApp requires/【placeholder】phone; Dashboard requires neither) updates required-ness and visible hints consistently; with JS unavailable the fields remain present and usable with sensible defaults.
- **Keyboard-only & assistive use**: All interactive elements (form fields, password toggles, remember-me, forgot-password trigger, social placeholders, tabs, remove/copy/create-alert buttons, alert edit/pause/delete/view/compare actions, notification toggles, change-password, logout, modal triggers) are reachable and operable by keyboard with visible focus; modals manage focus via the existing `window.TUI`; tab/result/status changes are announced via `aria-live`; icon-only controls have accessible labels; toggles expose `aria-pressed`/`aria-checked`.
- **Reduced-motion preference**: Tab transitions, modal open/close, card removal, button loading spinners, and any reveal animations respect the user's reduced-motion setting.
- **Duplicate / rapid actions**: Repeatedly copying a code, re-toggling a notification setting or alert status, re-submitting a form, rapidly removing items, or repeatedly opening/closing a modal produces consistent, non-duplicated visible feedback (no stacked broken states, no double-removal errors).
- **Honesty consistency**: No control or copy implies a real account/session was created, real data was stored on a server, a real email/WhatsApp notification was sent, a real password was changed/reset, a price is really being monitored, or a real API/payment is connected — every such surface is framed as تجريبية / واجهة أمامية فقط / قابل للربط لاحقًا.

- **FR-039**: Each page MUST meet WCAG 2.1 Level AA: AA contrast for text and meaningful UI, full keyboard operability with visible focus, focus management for modals via the existing `window.TUI`, meaningful image alternatives, labels and programmatically-linked error messaging for all form fields, accessible labels for icon-only controls, `aria-pressed`/`aria-checked` for toggles, `role="tab"`/`aria-selected` (or equivalent) for tabs, announcement of tab/result/status changes via `aria-live`, and respect for reduced-motion preferences.

**SEO & backend-readiness**

- **FR-040**: Each page MUST use semantic HTML with exactly one `<h1>` and a correct heading hierarchy, and the required document meta (Arabic title and meta description, language/direction, viewport, theme color, Open Graph baseline) appropriate to that page, plus the specified breadcrumb. Member/auth pages MAY mark themselves non-indexable (e.g., `robots noindex` where appropriate) since they are frontend-only, but MUST remain structurally SEO-correct.
- **FR-041**: All five pages MUST honestly reflect the frontend-only nature in copy and MUST NOT expose structured data or meta that asserts a real account, real session, real notification, real storage, or live pricing. Any optional structured data MUST be valid and consistent with the visible mock content.
- **FR-042**: Markup MUST remain semantic and backend-ready for later server-side template / accounts/notifications integration (predictable, stable structure; shared shell kept consistent with the other public pages; the `member-saved.json`, `price-alerts.json`, and `member-profile.json` catalogs usable as backend-ready reference data), with no dependency on a client-side runtime to render core content.

### Key Entities

- **Member (mock)**: A believable member identity — `name`, `email`, `phone`, `country`, `city`, `preferredLanguage`, `preferredCurrency`, a "member since" mock date, and a "تجربة تجريبية" status. Stored in the new `assets/data/member-profile.json` and reflected statically on `saved-deals.html` and `profile.html`; never implies a real account or session.
- **Saved Item (mock)**: A bookmarked entity of one of five types — **deal**, **coupon**, **destination**, **comparison**, or **article** — with `id`, `type`, `title`, type-appropriate context (image/alt, price/discount, source badge, status, expiry/date, counts), and a `linkUrl` resolving to the correct existing page (`deal-details.html?id=`, `coupons.html`, `destination-details.html?id=`, `compare.html?…`, `article.html?id=`). - **Price Alert (mock)**: A frontend-only watch — `id`, `type` (flight/hotel/package/destination), route/`destination` (with `from` when flight), `travelMonth`, `maxBudget`/target price, `travelers`, notification-method UI, email/phone placeholder, `status` (active/paused/triggered-mock), `currentSamplePrice`, and `lastChecked` mock date. - **Notification Preferences (frontend-only)**: The member's toggle states (email alerts, coupon reminders, price-drop alerts, saved-deal expiry reminders, WhatsApp placeholder, newsletter, weekly travel summary); part of the mock profile; toggling changes visible state only and never enables a real channel.
- **Auth Form State (frontend-only)**: The visitor's input on login/register/forgot-password forms, validated client-side with valid/invalid/error/success states; on valid submit produces a frontend-only confirmation and never creates a real account/session or sends a real email.
- **Member Session Context (mock)**: The notion of "being signed in" used only to frame the member pages with a mock identity; there is no real session, no auth gate, and no persistence — logout is a frontend-only toast/navigation.

## Assumptions

- **Scope is these five member pages plus navigation wiring**: This spec adds only `login.html`, `register.html`, `saved-deals.html`, `price-alerts.html`, and `profile.html`, and rewires the shell/homepage auth & member navigation to reach them. Merchant dashboard, SaaS owner admin, and any unbuilt about/contact/privacy/terms/partners pages remain out of scope and keep the "coming soon" affordance.
- **Foundation, homepage, discovery & content pages are reused, not rebuilt**: Spec 001 (local Tailwind build, Arabic-first RTL shell, header/drawer/footer, design tokens, reusable components, `window.TUI` utilities — `toast`/`modal`/`drawer`/`validateForm`/`copyToClipboard`/`prefersReducedMotion` — and `data-*` behaviors), Spec 002 (homepage + mock data), Spec 003 (discovery pages, `discovery.js`, `deals.json`/`coupons.json`/`compare-offers.json`), and Spec 004 (content pages, `content.js`, `destinations-full.json`/`articles.json`) are complete and consumed as-is. Additive mock-data files, additive imagery placeholders, and one additive `member.js` module are permitted; no existing shared behavior or section is changed or removed; `main.js`, `ui.js`, `discovery.js`, and `content.js` are untouched.
- **New JS module mirrors the discovery.js/content.js precedent**: Page logic lives in a new additive `src/js/member.js` scoped to the five member pages, loaded with `defer`, composing with `window.TUI` and `main.js`'s existing global `data-*` delegation; it adds only the new member-specific behaviors (tabs, item removal + empty-state toggling, alert create/edit/pause-activate/delete with custom modals, notification toggles, save feedback, password visibility, logout). Existing modules are not modified.
- **No real auth gate; mock member identity**: The member pages are directly reachable standalone public pages with no real "logged-in" gate or redirect; `saved-deals.html`/`profile.html` show a mock member identity from `member-profile.json`/static content. Login/register "success" is a frontend-only confirmation that never creates a real account or session.
- **Frontend/session-only state**: Saved-item removals, alert create/edit/pause/delete, notification toggles, and profile saves are visual/in-memory for the page view; reload restores mock defaults; `localStorage` MAY be used only as an optional frontend convenience and no copy claims permanent or server-side storage.
- **Static-HTML-first**: Each page's baseline content (auth forms; member header + initial saved items; initial alert cards; profile forms with mock values) is authored as static HTML that renders without a backend and without JavaScript; JS only enhances. Local JSON catalogs exist as backend-ready reference/mock data; pages do not depend on client-side fetch to show main content.
- **Login/register success behavior**: On valid submit, a success toast + inline success is shown (frontend-only) with a primary CTA to `saved-deals.html`; navigation to `saved-deals.html` MAY occur on confirmation but never via a silent redirect that mimics real authentication.
- **Data catalogs**: New `assets/data/member-saved.json`, `assets/data/price-alerts.json` (≥6), and `assets/data/member-profile.json` provide backend-ready reference data; saved items reuse existing deal/coupon/destination/comparison/article ids and links for consistency. All content is realistic but clearly not live.
- **Custom modals & no dialogs**: All confirmations and secondary flows (forgot-password, edit-alert, delete-confirmation) use the existing `window.TUI.modal` pattern; browser `alert()`/`confirm()`/`prompt()` are forbidden everywhere.
- **Source badges & safe labels**: Saved-deal/coupon surfaces reuse the source badges (Partner / Affiliate / Manual Deal / API Ready) and safe action labels consistent with the homepage, discovery pages, content pages, and constitution.
- **Product honesty**: All member identity, saved items, alerts, prices, statuses, dates, budgets, and notification settings are mock/demo and integration-ready, using the approved safe wording; the platform never claims a real account/session, server storage, sent notifications, changed/reset passwords, live price monitoring, connected APIs, or processed payments.
- **Language strategy**: Content is authored in Arabic (RTL) for this phase; structure stays English-ready and the existing language-toggle affordance in the shell is reused unchanged.
- **Accessibility target**: WCAG 2.1 Level AA, consistent with the foundation.
- **Browser baseline**: Modern evergreen browsers (Chrome, Edge, Firefox, iOS/macOS Safari), last 2 major versions, consistent with Spec 001/002/003/004.
