## Overview

This feature delivers the **first real management workspace inside the merchant (travel-agency) dashboard surface** of the Travel SaaS Platform. Spec 006 opened that surface with a single page — `dashboard/index.html` — that is both a client-presentable **overview** and the reusable **app shell** (RTL sidebar + topbar + mobile drawer + breadcrumb + page header + footer + empty/loading patterns). On that overview, every operational module (deals, coupons, bookings, customers, analytics, integrations, settings) was wired as **coming-soon**. Spec 007 builds the first two of those modules for real: **deals management** and **coupons management**, the core of what a travel agency actually does on the platform — publish and curate travel deals, and run discount coupons.

It creates **five new, fully-implemented pages** inside the existing `travel-saas-frontend/dashboard/` directory — `deals.html`, `create-deal.html`, `edit-deal.html`, `coupons.html`, and `create-coupon.html` — each reusing the **exact Spec 006 dashboard shell** (the same sidebar, topbar with notifications/quick-add/user dropdowns, mobile drawer + scrim, breadcrumb, page header, and dashboard footer), composed from the Spec 001 design language (tokens, cards, badges, buttons, forms, modals, drawers, toasts, empty/skeleton states) and the existing `window.TUI` utilities (`toast`, `modal`, `drawer`, `validateForm`, `copyToClipboard`, `prefersReducedMotion`) plus the `main.js` `data-*` behaviors (`data-coming-soon`, `data-modal-open/close`, `data-drawer-open/close`, `data-copy`, `data-toast`, `data-validate`, `data-frontend-form`). No new visual identity is introduced; no Spec 001–006 artifact is rebuilt, removed, or downgraded.

Two of the pages are **list/management screens** (`deals.html`, `coupons.html`): each presents a polished, app-like workspace with a page header (title + description + safe note + primary/secondary CTAs), a row of **stat mini-cards**, a **search + multi-filter** panel, a **sort** control, a **result-count + active-filter-chips** bar with `aria-live`, a responsive **table/card hybrid of at least 12 rows**, per-row **action menus**, a **bulk-selection + bulk-actions** bar, a branded **empty state**, a reusable **skeleton/loading** pattern, a **source/status legend**, and a **help FAQ (≥5)**. Three of the pages are **forms** (`create-deal.html`, `edit-deal.html`, `create-coupon.html`): each presents a professional, multi-section, mobile-friendly form with inline validation, dynamic repeatable fields, conditional helper text, slug/code/preview helpers, a **preview modal/card**, and a sticky action summary — with the edit-deal page additionally prefilled with realistic mock data and carrying an edit header, an activity mini-log (≥5 events), a public-preview link, and edit-specific actions.

All management logic is added to the existing `src/js/dashboard.js` **additively only** (no rewrite, no behavior change to existing dashboard features), dispatched per page by `<html data-page>` (`merchant-deals`, `merchant-create-deal`, `merchant-edit-deal`, `merchant-coupons`, `merchant-create-coupon`); `src/js/main.js`, `src/js/ui.js`, `src/js/discovery.js`, `src/js/content.js`, and `src/js/member.js` stay unchanged. The sidebar/topbar/quick-add links for the now-built pages (العروض → `deals.html`, إضافة عرض → `create-deal.html`, الكوبونات → `coupons.html`, إنشاء كوبون → `create-coupon.html`) are **rewired to real navigation** across the dashboard (including the Spec 006 `index.html` shell); the still-unbuilt merchant pages (`bookings.html`, `booking-details.html`, `customers.html`, `customer-details.html`, `analytics.html`, `integrations.html`, `settings.html`) remain **coming-soon**, and their files are not created. New backend-ready mock catalogs `assets/data/merchant-deals.json` and `assets/data/merchant-coupons.json` are added, reusing existing `deals.json`/`coupons.json` ids where useful.

Critically, every surface is **explicit and honest** that this is a frontend-only prototype: nothing is really published, no coupon is live on a real system, no data is saved to a database, no image is really uploaded, no affiliate/booking link is validated, no API is connected, no scraping source is active, no payment is processed, and no notification is sent. All such surfaces are framed with the approved safe wording (بيانات تجريبية / واجهة أمامية فقط / إجراء تجريبي / لا يتم الحفظ على خادم في هذه النسخة / قابل للربط لاحقًا بقاعدة بيانات / قابل للربط لاحقًا بمصادر Affiliate/API / لا يتم نشر العرض فعليًا الآن / لا يتم رفع ملفات حقيقية الآن / سيتم تفعيل هذا الإجراء لاحقًا مع الباك إند) while keeping each surface **integration-ready** for a future real backend and the markup semantic and backend-ready for later Django templating.

## Clarifications

### Session 2026-06-02

- Q: Where do the five pages live and how are paths resolved? → A: **Inside the existing `travel-saas-frontend/dashboard/` directory** (created by Spec 006), as siblings of `index.html`. Each page references shared assets/scripts with a `../` prefix exactly like Spec 006: CSS `../assets/css/tailwind.css`; icons `../assets/icons/sprite.svg`; images `../assets/images/…`; fonts `../assets/fonts/…`; scripts `../src/js/ui.js`, `../src/js/main.js`, `../src/js/dashboard.js`; public site `../pages/index.html` and `../pages/deal-details.html?id=<id>`. Inter-dashboard links resolve **within** `dashboard/` (e.g., `deals.html`, `create-deal.html`, `edit-deal.html?id=<id>`, `coupons.html`, `create-coupon.html`).
- Q: Do these pages reuse the Spec 006 shell or define a new one? → A: **They reuse the exact Spec 006 dashboard shell** — the same sidebar (brand + nav with the correct active item per page via `aria-current`), topbar (mobile menu button, breadcrumb/current area, company-switcher placeholder, global search, notifications/quick-add/user dropdowns), mobile drawer + scrim, breadcrumb, page header region, and dashboard footer — and **must not** use the public website's marketing header/footer. The shell stays backend-ready for later Django templating.
- Q: Where does the page logic live — a new file or the Spec 006 module? → A: **The existing `src/js/dashboard.js` is extended additively only.** New per-page controllers are dispatched by `<html data-page>` (`merchant-deals`, `merchant-create-deal`, `merchant-edit-deal`, `merchant-coupons`, `merchant-create-coupon`); no existing Spec 006 behavior is changed; `main.js`/`ui.js`/`discovery.js`/`content.js`/`member.js` are untouched; all scripts load with `defer`; no inline page JavaScript except JSON-LD or a safe inline JSON/mock-data block.
- Q: Must the pages render without JavaScript / without a backend? → A: **Static-HTML-first.** Each page ships its baseline content as static HTML that renders and is readable with no backend and with JavaScript unavailable: the list pages render their ≥12 rows and all sections statically; the form pages render all fields/sections statically (and edit-deal renders its prefilled values statically). JavaScript only **enhances** (search/filter/sort, chips, row/bulk actions, modals, toasts, repeaters, slug/code/preview helpers, conditional fields). The pages do **not** depend on client-side fetch to display their main content; the JSON catalogs are backend-ready reference data only.
- Q: Is any state persisted across reloads? → A: **Frontend/session-only.** Filter/sort/search state, selection state, a toggled status/featured flag, a duplicated row, an added repeater row, a typed form value, and a generated coupon code are visual/in-memory changes for the current view; reloading restores the mock defaults. `localStorage` MAY be used only as an optional frontend convenience, but **no copy may claim permanent or server-side storage** (لا يتم الحفظ على خادم في هذه النسخة).
- Q: How are confirmations and secondary flows handled with no browser dialogs? → A: **Custom modals/toasts only.** Delete and archive confirmations, the deal preview, and any assign/confirm flow use the existing `window.TUI.modal`/toast patterns; browser `alert()`, `confirm()`, and `prompt()` are forbidden everywhere on these pages — including the "generate random coupon code" action (no `prompt()`), which writes directly into the field.
- Q: How are deal/coupon "publish" and "upload" actions made honest? → A: **Publish is a mock action**, framed as نشر تجريبي / لا يتم نشر العرض فعليًا الآن — it validates the form and shows a success toast/state but never claims a real publish, and the public site is not actually mutated. **Media upload is mock** — a placeholder/preview UI with no real file upload (لا يتم رفع ملفات حقيقية الآن); a local object-URL preview MAY be shown for UX, but no file is sent anywhere. Affiliate/partner/API/source URLs are **configuration-ready only**, with explicit "no link validation happens now" helper text (قابل للربط لاحقًا بمصادر Affiliate/API).
- Q: How do the not-yet-built merchant pages behave, and which links change? → A: **Only the now-built deals/create-deal/coupons/create-coupon (and edit-deal) links are rewired to real navigation** (across the dashboard shell, including Spec 006 `index.html`); every control targeting a still-unbuilt merchant page (`bookings.html`, `booking-details.html`, `customers.html`, `customer-details.html`, `analytics.html`, `integrations.html`, `settings.html`) keeps **coming-soon** behavior (visible toast, no navigation to a non-existent file), and those files are not created. No control is dead and no link 404s.
- Q: How is the edit-deal page parameterized? → A: It **MAY accept `?id=<deal-id>`** to choose which mock deal to prefill (resolving against `merchant-deals.json`/`deals.json` ids); if the id is missing or unknown, it **falls back to a default mock deal** and never errors or 404s. Its public-preview CTA targets `../pages/deal-details.html?id=<id>` when the public deal page exists, otherwise shows a safe toast.

## User Scenarios & Testing *(mandatory)*

The beneficiary is the same **travel-agency merchant user** introduced in Spec 006 (an agency owner, manager, or agent — Arabic-first, mobile-capable). Spec 006 gave them an app-like overview; Spec 007 gives them the **operational workspace** where the bulk of their day-to-day work happens: managing the agency's catalog of travel deals and the discount coupons that drive bookings. Here the merchant can browse, search, filter, sort, and bulk-manage all of their deals; create a new deal through a complete professional form; edit an existing deal with its history visible; manage their coupons (including copying codes and bulk operations); and create a new coupon with a live preview — all as a believable, clearly-mock, frontend-only prototype that is backend-ready. The feature also serves the **business** by making the platform's merchant value proposition concrete and client-presentable, demonstrating the full deals/coupons management lifecycle without faking any real publish, save, upload, validation, integration, payment, or notification.

### User Story 1 - Manage the agency's deals from a powerful list (Priority: P1) 🎯 MVP

A travel-agency user opens `dashboard/deals.html` from the sidebar (العروض) and lands in a professional, app-like deals workspace inside the familiar Spec 006 shell. A page header states `إدارة العروض`, explains this is the agency's deal-management workspace, carries primary/secondary CTAs (إضافة عرض جديد، تصدير تجريبي، استيراد تجريبي), and notes the actions are frontend-only. A row of **stat mini-cards** summarizes the catalog (total, active, drafts, scheduled, paused, expired, nearing-expiry, total clicks, booking inquiries, coupon copies). A result-count + active-filter-chips bar updates live (`aria-live`), the table collapses to usable stacked cards on mobile, an empty state appears when no deal matches (with reset + create CTAs), and a skeleton pattern, a source/status legend, and a help FAQ (≥5) are present. Every control is live — never dead, never a browser dialog.

**Why this priority**: The deals list is the **center of gravity of the merchant workspace** — the screen an agency lives in daily and the part most judged in a client demo. It proves the reusable list-management pattern (stat cards + filters + sort + result-count/chips + table-card hybrid + row actions + bulk actions + empty/skeleton + legend + FAQ) that the coupons list and every future merchant list page (bookings, customers) will reuse. It depends only on the Spec 006 shell and the mock deal data, and is the most self-contained, highest-value slice — the demonstrable MVP of this phase.

### User Story 2 - Act on a deal: row actions & bulk operations (Priority: P1)

From the deals list the merchant takes action. Each row's **action menu** offers: **view public page** (→ `../pages/deal-details.html?id=<id>` when the public page exists, else a safe toast), **edit** (→ `edit-deal.html?id=<id>`), **duplicate** (toast and/or a visual copied row), **pause/activate** (toggles the visible status badge), **mark featured/unfeatured** (toggles a featured badge), **archive**, and **delete** (a **custom confirmation modal** — never a browser `confirm()`). A **bulk-selection** bar with a select-all control shows the selected count and offers **bulk activate, bulk pause, bulk archive, bulk delete (custom confirmation modal), and bulk export (mock)**. Every action produces visible frontend feedback — navigation, a toggle, a toast, or a modal — and none is dead; nothing claims a real publish, deletion-from-database, or export-to-file happened.

**Why this priority**: Row actions and bulk operations are what make the list a true **management** surface rather than a read-only report — they prove the row-action-menu, status/featured-toggle, duplicate-feedback, custom-confirmation-modal, and bulk-selection patterns that the coupons list and future merchant lists reuse, and they exercise the no-browser-dialog and no-dead-control rules heavily. They are co-essential with US1 (the list itself) and independently testable against the mock deal data.

**Independent Test**: On `dashboard/deals.html`, open a row's action menu and confirm it offers view-public-page, edit, duplicate, pause/activate, mark-featured/unfeatured, archive, and delete; confirm edit navigates to `edit-deal.html?id=<id>`, view-public-page navigates to `../pages/deal-details.html?id=<id>` (or shows a safe toast), duplicate shows a toast (and/or a visual copy), pause/activate toggles the status badge, featured toggles the featured badge, and delete opens a **custom** confirmation modal that (on confirm) removes the row visually with a toast. Confirm select-all + per-row checkboxes drive a selected-count bar offering bulk activate/pause/archive/delete (delete via custom modal) and bulk export (toast). Confirm no action is dead, no `confirm()`/`alert()`/`prompt()` fires, and no copy claims a real publish/delete/export.

**Acceptance Scenarios**:

1. **Given** a deal row, **When** the user opens its action menu, **Then** it offers view-public-page, edit, duplicate, pause/activate, mark-featured/unfeatured, archive, and delete — each operable and none dead; the menu is keyboard-operable and closes on outside-click/Escape.
2. **Given** the edit action, **When** activated, **Then** it navigates to `edit-deal.html?id=<id>`; **Given** the view-public-page action, **When** activated, **Then** it navigates to `../pages/deal-details.html?id=<id>` when that public page exists, otherwise shows a safe frontend-only toast — never a 404.
3. **Given** the pause/activate action, **When** activated, **Then** the row's status badge toggles between Active and Paused in place with a toast; **Given** the mark-featured action, **When** activated, **Then** a featured badge toggles on/off in place with a toast — neither claiming a real publish/state change on a live system.

- **Deal Form Draft (frontend-only)**: The in-progress field values, repeater rows (highlights, included/not-included), media placeholders, slug/SEO preview, and status/visibility selections on create-deal.html/edit-deal.html; validated inline; save-draft/publish are mock; nothing is persisted server-side.
- **Coupon Form Draft (frontend-only)**: The in-progress field values, generated code, discount/source/scheduled conditionals, and the live preview card on create-coupon.html; validated inline; save-draft/publish are mock; nothing is persisted server-side.
- **Deal Activity Event (mock)**: An entry in edit-deal.html's activity mini-log — a type (created/updated price/status changed/coupon attached/inquiry received), text, and relative time; at least 5; a demo history, not a real audit trail.
